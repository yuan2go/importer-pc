# SM 按小车到位分轮与启停心跳设计

状态：本次实现契约。依据：2026-11-12 用户确认的 RCS 调度及异常恢复要求。现行轮次、心跳与格式文档随本次实现一起更新，历史验证仍仅对原提交负责。

连续上件时，短于 800 ms 的空盘画面可能无法形成可信移出，导致后一件沿用前轮而被抑制；同码最容易暴露问题，但换码也不能可靠解除该抑制。把有效 RCS 相机编码对应的小车到位身份作为自动分轮依据，空盘检测不再承担这条路径的换件判定。每次到位最多接纳一次生产提交，条码相同也可在下一辆车上正常提交。

在下述调度契约成立时，这个方向能消除对空盘持续时间的依赖。实际读码成功率与吞吐仍取决于相机图像、缓存切换、放稳时间和心跳响应，须分别验收，不能据设计宣称已经解决现场全部漏读。

## 已确认的 RCS 契约

| 项目 | 已确认内容及影响 |
| --- | --- |
| 一车一件 | 下一件包裹的小车号一定改变；每辆车本次到位只承载一件。 |
| 到位保持 | 未收到本位取格口请求且投递位未停用时，小车一直等待。供包台尚未发现的新车不会自行按节拍通过。 |
| 目标绑定 | RCS 先将取格口请求绑定当时位置上的车，再放车并安排下一辆。供包台不增加车号参数或远端锁车协议；未撤车期间可信换车可证明旧请求已绑定。 |
| 请求编号 | RCS 原样返回供包台发送的 `requestId`，只可用于匹配本次报文，不能证明一次新的小车到位。 |
| 调度单位 | 按 `bcrCode` 独立控制；左右 `stationCode` 相同也可独立停用。 |
| 心跳成员 | 心跳包含某位表示继续调度；移除该位后不再安排小车，已在位小车也会调走。 |
| 空心跳 | 接受 `data: []` 并正常响应，因此两位停用仍可确认 RCS 连接。 |
| 成员确认 | 成功响应前已应用本次成员集合。完整确认且串行完成的成员变更可据此同步；超时旧报文仍可能迟到生效，不能用后续成功响应证明其已经取消。 |

心跳车号按“当前相机下的小车”使用，不把未来计划车辆当作已到位。客户 RCS 联调必须核对真实回包与这一含义一致；目前没有远端到位序号或状态生成时间的证据。

## 身份与一次提交

| 身份 | 用途 |
| --- | --- |
| 心跳 `requestId` | 校验一问一答；每次心跳不同，不触发新轮次。 |
| `stationCode`、`bcrCode`、`agvNo` | 标识某位当前观测的小车；同一车号重复返回只更新确认时间。 |
| 本位到位代次 | 复用本位周期账的 `Generation`，记录相邻到位变化，关联当前车号和已提交事实。A→B→A 是三次到位，不按车号全局永久去重。 |
| `RoundId` | 本次包裹识读与处置，关联条码、图片、输入和原请求。空车到位不立即创建包裹轮次。 |
| `OperationId`、`CommandId` | 原请求和命令防重；换车、重启或关闭页面不重发原请求。 |
| RCS 返回任务号 | 记录与排查字段，不用来推断到位、离位或重新提交资格。 |

在现有本位周期账增加必要的车号、到位依据、提交占用与来源关联，不另建一套包裹业务账。到位切换、本轮结束和自动资格改变使用现有存储事务，首次提交同时占用本轮和本次到位资格。相机、PDA、键盘竞争同一个提交权；即使页面已复位，人工再次回车也不能绕过本次到位的一次提交限制。

人工命令也须绑定输入所属的位、到位代次及目标轮次。换车期间已排队的回车、尚未完成的 PDA 字符串和旧按钮命令不能提交到新车；保留的未提交文字只作为草稿，须由新到位下的明确人工操作重新提交。原 CommandId 重放继续返回原结果。

## 正常供包流程

1. 心跳通过本次编号、命令、结果序号、站点和相机编码校验，取得有效且未过期的车号。接收端同时核对当前 RCS 配置代次、本位启停版本和本次实际发送的成员集合。
2. 首次建立可信到位基线，或连续有效观察中车号从 A 变为 B 时，登记本位到位代次。相同车号重复响应、IDLE/TASKING 切换、无码、换条码和画面变化都不产生新代次。缺少车号不是“空位”，不能先清空身份再把同一车号当作新车。
3. 换车时结束 A 的当前展示与放置责任，保留其原请求；关闭旧帧提交资格，完成下节规定的相机缓存切换，B 才取得自动读码资格。只有这一到位边界重开本位自动提交，不再等待连续空盘 800 ms。
4. 空车 B 可以一直等待，不启动 1000 ms 识读倒计时。可信上件、首个可用于业务判断的候选或完整人工提交，沿既有规则建立包裹轮次；只识到排除底码或始终无可信上件、无正式候选时保持等待。放稳、筛选、图像保存等仍消耗已开始的识读期限，不因新帧续期。
5. 首次提交持久接纳后锁定本次到位。随后重复同码、换码、重新放置、PDA 回车或画面曾经空盘，都只观察或反馈已处理，不追加生产请求。到期未提交可在本次到位原位人工补录。
6. RCS 调走该车，下一辆车到位后重复上述流程。新车即使条码与上一车相同，也创建独立包裹请求。

车号确认是配置了有效 `bcrCode` 的生产位的提交前提；相机未配置或断线时，人工提交仍可使用本位有效到位身份。没有相机编码的既有人工来源保留原独立路径，不新增全站车号依赖。缺少本位有效车号时展示等待确认，保留人工输入与相机预览，不反复制造“扫描未受理”记录。IDLE/TASKING 文案继续作提示，不能用状态文字代替车号及到位依据。

## 换车时保证图像属于新车

仅在 Application 放开自动抑制不够。当前 `MvsAcquisition` 在已校准但未确认在位时也会阻止正常解码；这项门槛必须随分轮方式一起调整。有效到位且完成缓存切换后，两种识码路线都可按放稳规则识读，不再要求空盘参考先确认在位。沿用静态参考时，新到位或新会话须先在本次边界下确认与参考一致的空车，才允许该模型的 Present 建立无码轮次，防止不同小车底纹被当作包裹；正式候选仍直接按放稳识码，不等待空盘。独立核验的物理证据保留原含义。已有视觉证据可辅助上件、图像质量和诊断，但不能作为第二条并行的重新提交通道。没有可靠视觉上件时间时，仍按首个正式候选的既有降级规则起算，不虚构实际投包时刻。

换车切换必须在当前相机所有者内完成：

1. Application 先关闭该位自动接纳，标记新的到位代次，旧代次的观察即使晚到也不得获得新轮次提交权。
2. 在采集循环的安全边界等借用帧释放，排空旧软件解码工作和交付缓存，再调用现有 SDK 清缓存能力。复用 `MvsInspection` 已有的边界处理语义及 `IMvsApi.ClearBuffers`，不要为每辆车重连相机或借用调试会话身份。
3. 清缓存成功后记录相机会话、边界代次和帧身份，重置本次放稳累计。之后取得的新帧携带该到位代次直到交付、原图保存和持久接纳；每一步继续使用原来的会话及时效守卫。
4. 切换期间若又收到新到位、停用、管理暂停或相机重连，按最新身份决定是否开放。旧切换完成回调不能开放新会话。清缓存失败则本位暂停自动接纳并明确原因，保留原设备所有权，不伪报成功。

不能用解码完成时间证明采图发生于新车到位后。当前 `Observation.DecodedTicks` 含解码时序，不能冒充采集时钟；需要携带采集阶段的身份和主机单调时间，并以已完成的 SDK 缓存边界建立关联。SDK 返回时间也不等于传感器曝光时间，真实库是否仍返回边界前的缓存图必须实测。MVID 路线使用原始采图排空队列、不对丢弃帧识码；其有限排空失败必须如实报告。软件路线和原生路线分别覆盖这一测试。

## 心跳与投递位启停

心跳成员控制调度，空心跳确认连接；按下表选择报文成员。停用不加入空盘条件。

| 本位状态 | 接纳本位新条码 | 心跳包含本位 `bcrCode` | 完成条件 |
| --- | --- | --- | --- |
| 启用 | 按正常业务守卫 | 是 | 正常供包。 |
| 停用中 | 否 | 是 | 等本轮已开始调用、执行及回执落盘收口；不等空盘，不等 Unknown 变为成功。 |
| 已停用 | 否 | 否 | 主动停止并释放相机，保留原请求及防重账。 |
| 两位均已停用 | 否 | 发送 `data: []` | 仍按真实响应维护 RCS 连接确认。 |

停用中暂保留成员，避免原取格口调用尚未到达 RCS 时先通知调走目标车；收口后移除。没有开始发送尝试的请求不得发送，可直接停用；本轮已经收口也直接停用。新车在停用中到位不能接纳新件。点启用可以取消停用，但不重置已提交车号的防重资格。

自动心跳和手动检查共用当前成员选择及现有单在途互斥。启停变化合并为一次待执行的成员刷新，取得发送许可后读取最新快照，不排队累积旧成员报文。已有心跳结束后尽快发送最新集合；不能通过取消本地等待声称已撤销远端收到的旧心跳。远端停用是否生效只能由包含新集合的实际交互确认，网络失败时记录同步未确认。

切换前在途响应可以保留真实连接证据，但不能恢复已停用位提示或到位资格；启用后须取得匹配当前成员版本的新响应。缺少某位有效编码就不编造该位身份；RCS 地址及必要协议配置有效时，即使成员为空也可发送空心跳。空心跳响应须按编号和协议结构校验，不能只因 HTTP 200 就推断业务确认，更不能生成小车状态。

## 异常、恢复及原请求

| 场景 | 处置 |
| --- | --- |
| A 请求已开始，B 已有效到位，A 回包晚到 | 可信换车结束 A 的当前放置，允许 B 独立处理；A 按原报文、原目标、原期限收尾，结果只写原记录。 |
| A 已失败或 Unknown，随后可信换车 | 换车作为放置结束依据，解除 A 占据当前位的责任；不改写请求结果，不重发。Unknown 仍须满足调用、回执等实际收口条件才进入历史保管。 |
| 失败后没有可信换车 | 保留当前人工处理及“已取下包裹”守卫；点击可以结束放置，不能给同一已提交到位再增加请求。 |
| 相机重连，但 RCS 到位连续有效 | 不增加到位代次；重新建立相机会话和缓存边界，已提交到位仍被抑制。 |
| RCS 断线、结果缺失、身份不符或过期 | 本位自动提交暂停并撤下绿色可投包提示；不把失联当作离位，不擦除最后已知车号及提交事实。 |
| 恢复后车号不同 | 新的有效响应可作为新到位依据，重新执行缓存边界；旧请求仍按原责任保管。 |
| 恢复、重启或重新启用后车号相同 | 不据此证明新到位，保留已提交抑制。失联期间可能发生 A→B→A，现协议无法区分，不能猜测。 |
| 初次基线或升级后缺少车号关联 | 仅在没有原当前责任和自动抑制时建立可接纳的新基线；不能用首次心跳清除旧防重。关联不足时明确提示并按原人工处置流程收口，不能自动补发。 |
| 管理中心、调试或另一位活动 | 保留各自身份与现有权限守卫。生产暂停不借调试结果创建到位；调试明确发送仍是独立请求，不能意外释放生产提交权。 |

同一车号在连续会话内重复返回没有歧义；连续观测的 A→B→A 也可正常分轮。跨失联只看到 A→A 时，`requestId` 无法填补缺失的到位证据，保守保持抑制可能需要人工排查。这是现有协议的边界；若现场要求该场景也全自动恢复，再由 RCS 提供每次实际到位的唯一编号，不能在供包台用新心跳编号替代。

完整备份前持久冻结心跳成员租约，复制期间继续真实心跳但不改业务快照、不应用换车；备份中未收口租约按可能存在远端效果保管。维护核对命令绑定运行、位、到位代次、启停版本、目标请求及责任令牌，旧窗口不能解除新责任。

本次到位账须随现有恢复账持久化，重启不重新赋予已接纳请求提交权，不回放旧相机事件。只支持当前数据格式；若实现需要修改业务格式，须更新格式标识并在写入前拒绝旧格式、保留原件，不在本功能中增加隐式迁移。

## 时序与吞吐

当前心跳默认 1000 ms，可配置到 100 ms。周期选择须依据客户允许频率及现场响应测量。

发送周期与响应预算分开：保持有限的 3000 ms 总响应预算及单在途，不增加一个新的现场设置项。慢响应期间不并发补发，不积压周期任务。车号有效期为实际有效响应时间加 `max(3000 ms, 3 × 周期) + 3000 ms`，不能因读取本地状态或长时间等响应而续期；连接有效与本位到位有效分别判断。

新车未获请求会等待，所以正常启用且链路有效时，较慢的心跳主要造成下一车等待与上件反馈延迟。提高心跳频率有助于吞吐，但是否采用 500 ms 或更短周期，取决于客户允许的请求频率、实际响应分布和目标节拍；当前没有这些测量数据，不承诺固定毫秒级响应。首次启用、成员切换和手动检查可触发一次合并后的即时检查，不修改原取格口请求或自动重试它。

每车记录到位响应接收、缓存切换起止、首个新帧、可信上件或首候选、首次接纳、发送尝试、完整响应等时间，并关联位、车号、到位代次、RoundId、请求号及返回任务号。直接测量端到端与实际连续心跳间隔，不相加各阶段 P95。

## 实现范围与远端不确定性

| 位置 | 必要改动 |
| --- | --- |
| `Ipc.Integrations.SportmasterRcs/RcsHeartbeat*.cs` | 按启停选择成员、支持空心跳、校验响应及成员版本、独立响应预算；保留单在途及原请求隔离。 |
| Application 契约与 `Ipc.Application.ParcelFlow/ParcelSmRounds.cs` | 以明确类型传递有效车号观察，持久化到位关联，原子切换当前轮次与一次提交权；视觉不再重开本路径。 |
| `Ipc.Application.ParcelFlow/ParcelPositionControl.cs` | 沿当前调用/回执收口逻辑选心跳成员，保留无空盘停用和真实资源释放语义。 |
| `Ipc.Drivers.Hikrobot.Mvs` | 在既有采集所有者中提供生产到位缓存边界，携带帧所属代次，调整空盘依赖，保留放稳与两种识码路线。 |
| 现有存储、快照及诊断 | 持久化必要身份；页面按当前轮次显示，记录可关联车号与到位依据，不展示旧轮回包为新件。 |

删除按空盘重新开放有编码生产位的路径及其专属预期；人工无编码路径和视觉诊断保留。调试真实发送也接管目标位的一次提交与发送责任，不能借独立记录绕过目标协调。无编码请求仍按站点与位置协调，不能推定远端隔离。

本地 HTTP 超时、取消及落盘不证明 RCS 不会迟到绑定目标；收到新的成员确认也不能证明超时旧心跳不会晚生效。发送前持久登记相关位置的原请求/成员意图，完整有效确认后收口。换车或撤车时若存在仍可能改变目标的原请求，或改变成员时尚有结果不确定的旧成员意图，仅相关位进入远端责任待核对；不能用快速启停、固定等待、同码人工输入或调试绕过。历史保管且已脱离当前目标责任的 Unknown 不重新加锁。

业务拒绝留车或确证未尝试请求：先取下包裹，停用本位，等待实际成员移除确认，再启用并等到可信的新车号；同车未提交可在恢复确认与相机边界后继续原轮，已过期仅人工补录。远端责任不确定时，由维护核对客户 RCS 原请求执行/取消及成员状态，留下外部核对依据，再明确解除对应位该次恢复围栏；此人工核对不是软件自动证明。没有客户证据时保持待核对，另一位独立生产。

## 验证与现场验收

已完成的分析证据：现有生产空盘模型在合成回放中，400 ms 空盘（实际样本跨度 360 ms）及 800 ms 空盘（跨度 760 ms）均未输出可信移出；1000 ms 空盘（跨度 960 ms）可以确认移出。这只证明模型连续性门槛，不构成本次到位分轮的验证，也不是客户 RCS 端到端测试。

实现后的本机回归至少覆盖：

- 连续同码和异码、无空盘及小于 800 ms 空盘：A/B 分别一次请求；同车反复识码、提起再放和人工竞争均只一次。
- 空车长期等待不超时；排除底码不建件；无码、多码纠正、期限与人工补录按原规则工作。
- A→B→A 正常循环；重复、缺项、错误编号、错误编码及旧成员回包不制造新代次；两位互不阻塞。
- 在 SDK 队列、识码线程、Application 交付、原图保存各处分别阻塞旧 A 帧，换到 B 后确认旧帧零提交；清缓存失败不伪造就绪，两种相机路线分别通过。
