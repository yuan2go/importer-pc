# 作业卡状态与现场验收

本文写 SM 双工位作业卡现在的行为，以及在真实工控机上验收“看得清、操作快、不误导、易恢复”的方法。状态的判定顺序以代码为准（`StationSlotContinuity.DisplayPresentation`、`ParcelPresentation.Operation`），本文只做现场可读的摘要；行为变了就直接改本文。

## 阅读顺序

每个工位卡片从上到下：工位名和相机连接 → 当前条码（输入框）→ **结果区**（状态符号 + 状态文字，下方是格口号或原因）→ 下一步 → 波次、任务、商品、返回数量 → 提交 / 查看详情。

- 结果区始终回答“现在该做什么”。取得格口时格口号是全页最大的字（6 字符以内 72/56 DIP，空间不足只按比例缩小）；没有有效格口时这里换成原因，不留旧格口。
- 状态用文字表达，颜色辅助识别。需要符号的结果区使用成功 ✓、需处理 !、未确认 ?、处理中 ◷。已确认的 RCS 业务拒绝使用与等待投包一致的浅灰居中布局，深红标题显示接口消息，完整条码显示在输入框，结果区不重复显示条码摘要。
- 左卡永远是左工位，右卡永远是右工位；一个工位的故障先显示在本卡，顶部只加一句摘要（如“左位相机离线，可手动输入”）。

## 状态表

从上往下，先满足的生效。

| 状态 | 结果区显示 | 下一步 / 可用动作 | 可以放下一件吗 |
|---|---|---|---|
| 状态已失效（界面与后台断开） | 灰色“状态中断 · 旧格口已失效”，不显示格口 | 等待自动恢复；一直不恢复时通知维护 | 否 |
| 供包已暂停（维护、备份时） | “供包已暂停”。当前件已有拒绝或未确认责任时保留该结果 | 本件暂勿投递，等待恢复 | 否 |
| 相机离线 / 恢复中 | “相机离线 · 可手动输入条码”（不允许手动时“本位暂停供包”） | 自动重连，不需要点击；可用扫码枪/键盘补录；故障无法恢复时通知维护 | 只能手动补录 |
| 当前没有可用条码 | 可用位显示居中“等待投包”；受阻时显示本位状态 | 条码朝上放包裹；也可输入完整条码 | 按本位准入 |
| 本次读码已失效 | “本次读码已失效” | 本件暂勿投递，重新扫描 | 重新扫描后 |
| 处理中 | “处理中…”，不显示上一件格口 | 等待 | 等本件结果 |
| 格口已取得 | 大号格口号 + 下方四项任务信息 | 按本次格口投递 | 本件投递后 |
| 当前件未分配格口（关联的 RCS 已确认业务拒绝） | 居中显示 `msg` / `message` 原文。缺少消息时显示“RCS 未分配格口”。长消息可换行、滚动和复制。标题下显示“本件暂不能分配格口”及细线 | 细线下分行显示取件说明和维护提示。原请求选择人工处理时先判断包裹。暂停、RCS 离线或停用中将维护提示换成当前限制 | 按本位当前准入 |
| RCS 未连接 · 本次请求未送达 | 未送达说明 | 连接恢复后取下包裹再重新放上 | 恢复后 |
| 格口未确认（请求已发出，结果不确定） | 浅灰区居中显示“格口结果未确认”，说明本件未取得可用格口或新扫码未发送 | 取下包裹，等本位恢复后再上件。相机无法提供放置证据时可点“已取下包裹” | 本次放置结束后可以，同码重放创建独立请求 |
| 多码、规则拒绝或扫码过期 | 浅灰区居中显示具体原因和本件未发送的说明 | 核对条码或查看本次图片，按提示取件后再上件 | 按本位当前准入 |
| 等待包裹 | “等待包裹” | 放上包裹 | 是 |

一次放置只请求一次。作业卡在没有可用条码时按当前准入显示等待投包或阻断状态，取件过程不插入独立的“未读到条码”页面。确认空托盘才释放本次放置的防重责任，停用中的投递位才可完成停用。通过身份、时效和筛选校验的不同条码也是换件证据，新件不被上一件未确认结果阻断；同次重复观察及多码拒绝的部分读出不算换件。旧请求和回包只在记录中核对，内部异常只进入诊断日志。

## 输入

- 扫码枪文字自动送到最近选中的工位，回车提交；点击卡片任意区域，或按 **F2（左位）/ F3（右位）**，选择输入位置。
- 上一次提交还在处理时，新扫描不接收，并提示“结果出来后请重扫”；不会拼接到上一码。
- 离开作业页、切换窗口或打开其他输入控件时不抢焦点。

## 供包节奏

一件包裹从放上到显示格口，依次经过：

1. **放稳**：画面静止达到“放稳后再识别”时间（默认 200 ms）。放置过程中的帧只预览、不识别；画面一直不稳时约每 1.5 秒仍识别一次。
2. **识别一帧**：耗时由“需要识别的条码种类”决定。合成基准（3072×2048，4 核）下常用一维码（Code128 + Code39 + EAN13，新站默认）约 150 ms；“全部码制”约 1.5 s，这正是现场曾测到的约 1.5 秒一帧。早于新默认配置的站点若仍是“全部码制”，需要在设置里改为实际使用的码制。
3. **取格口**：向 RCS 请求一次，耗时取决于 RCS。
4. **下一件**：换成另一个条码立即算新的一次；同一条码拿走再放，要先判定空托盘（连续 3 帧无码且不少于 800 ms）。

包裹一直放在相机下、小车不动时，只请求一次 RCS，直到包裹被拿走：

- 画面没有变化、只是几帧没读出码（反光、标签边缘），不算空托盘，不会重复请求。
- 相机断线重连后读到同一个码，仍是同一次放置：不重复请求，作业卡恢复显示原格口，不用拿起重放。
- 软件重启开启新班次。仍占位的未决包裹保持原请求守卫。已离位且执行与回执责任收口的历史未确认记录，在“记录”核对。

现场在“设备与诊断”的“技术详情”里看两个数：每台相机的“单帧识别耗时”（超过 600 ms 时提示改码制），以及“取格口耗时”的中位数和 P95。两者相加再加约 0.2 秒放稳时间，就是一件的等待时间。

## 现场验收

请没有参与开发的操作员，在真实工控机、实际 Windows 缩放和实际站位下完成。记录第一次停顿、看错、重复点击和开口询问的位置，这些就是下一轮的改进点。

| 场景 | 做法 | 通过标准 |
|---|---|---|
| 第一眼 | 打开软件后直接问：哪个工位要处理、格口是多少、下一步做什么 | 约 3 秒内答对 |
| 看清格口 | 在实际站位量出能看清格口号的最远距离；分别看 100% / 125% / 150% 缩放 | 实际站位能看清；记下最远距离 |
| 连续供包 | 左右各连续放 20 件，含同一件放着不动、拿走再放；记下“单帧识别耗时”和“取格口耗时” | 每件不新增点击；同一件不重复请求；空托盘后回到“等待包裹”；放上到出格口的等待操作员可以接受 |
| 新旧切换 | A 取得格口后立刻换 B | B 出结果前看不到 A 的格口 |
| 扫码枪 / PDA 连扫 | 快速连扫 A、B；用 F2/F3 切换工位后再扫 | 不拼接、不丢失、不落到另一工位 |
| 相机断开 | 拔左相机网线 1 分钟再插回 | 只有左卡提示；右位照常；插回后自动恢复，不需要点击 |
| RCS 停止 / 超时 | 停 RCS 服务；再让 RCS 响应慢于“RCS 请求超时” | 未送达与未确认分开显示；未确认不自动重发；记录页可查到本件 |
| 重启 | 正常关闭再打开，分别核对仍占位和已离位的未决请求 | 直接进入作业页；仍占位保留原守卫，已离位且收口的历史只在记录可查 |

结果按 AGENTS.md 分开记录：Windows 实机、真实 SDK、客户 RCS、现场验收，没做的写“未运行”。
