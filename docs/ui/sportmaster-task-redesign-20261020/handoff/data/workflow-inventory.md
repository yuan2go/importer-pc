# Sportmaster 作业、记录、支持与安装入口：截图证据与交互迁移

本清单已通过 `view_image` 实际逐张查看 22 张图像；其中 `22-auxiliary.png` 与 `02-workstation-normal.png` 内容及哈希相同，保留其入口来源，但不把它算作一个不同界面。主审查的 14 张维护与首配截图由参数清单覆盖。

证据只覆盖截图。附件自述来源为冻结提交 `0e79e73bdb6d7a1702373963295b192a803f28e7` 的 WPF 视觉树渲染，并使用合成数据；此处没有读取该版本源码，没有核实按钮调用或生产链路。所有重设计状态和数值必须标注模拟。

## 1. 可以保留的设计和优先问题

**保留：** 左右投递位的空间对应；“本次条码”和“目标格口”绑定在同一位置；等待、处理中、取得格口、结果待核对、业务拒绝、状态失效有不同可见表达；处理中不显示已取得格口，失效时使用“旧格口已失效”替代旧格口；未知结果明确提示不要重复放货；作业记录是查询快照；支持摘要有预览与保存两步；正常作业没有每包确认按钮。

**优先问题：**

1. `02-workstation-normal.png` 中格口、条码与状态被放在大块空白上方，结果的实际阅读面积利用不足；`after-normal-1100.png` 与 `after-normal-900.png` 又将格口挤到狭窄列中，示例 `REFERENCE-07` 被拆行，主信息密度随窗口变化失衡。
2. `01-workstation-waiting.png` 至 `03-workstation-details.png` 顶部同时展示“暂停新入场”“恢复新入场”；卡片底部常驻“查看详情”“核对原请求”“继续原阶段”。这些不同频率、不同风险的操作视觉权重近似，而且作用对象与状态条件需要读懂内部概念。
3. `after-left-processing-right-valid-1366.png` 顶部“作业就绪”和左侧“正在取格口”并存；`after-workstation-blocked-login.png` 顶部有作业阻断而两侧仍是绿色取得格口。各个状态可能分别正确，但用户要自行分辨“新包能否进入”“当前包结果”“相机读码状态”三层含义。
4. `03-workstation-details.png` 展开后直接出现驱动键名、GUID、观察来源和英文原因，适合诊断但不帮助操作员第一时间选择下一步；用固定详情入口提供“当前包过程 + 结果原因”，技术原文按需展开。
5. `05-history-filters.png` 筛选展开后表格跌出主要视区；`after-history-filters-minimum.png` 甚至只见筛选和查询工具条。普通记录查询被高级时间原文、UTC 偏移、原请求 ID、快照统计挤占。
6. `04-history.png` 列表中的 `left/right`、UTC 偏移与半截格口不利于现场阅读；“核对所选原请求”和“继续所选未尝试阶段”应跟随一条明确选择的异常记录，只在适用状态出现。
7. `after-support-invalid-date.png` 已有日期字段错误，却又出现“时间必须带明确时区”的总体错误。截图能证明有错误表达，不能证明其错误映射正确；设计应将日期/时间/时区/范围错误分别定位，保留其他输入。
8. `published-startup.jpg` 将来源、完整性、提权、旧部署保留等工程解释集中放在入口；用户的首要任务“检查当前安装介质并继续”需要有清楚进度与结果。保留可信来源、摘要和诊断，但放到检查结果或按需详情中。

## 3. 原字段与操作迁移（作业、查询、支持、安装）

| 原功能/字段 | 新位置 / 名称 / 控件 | 作用对象与解释 |
|---|---|---|
| 工作台、作业记录、设备与维护、帮助与支持 | 主导航：作业、记录、设置、诊断与支持；首配独立入口 | 四类长期任务；首配完成后直接进入作业，不重走向导 |
| reference-17 / 工作站名 | 全局工作站身份行 | 与当前Application一起始终可見；示例不可成为默认 |
| 左投递位/右投递位、left/right | 左投递位 / 右投递位（L/R作为辅助） | 空间布局固定；左侧不因排序或异常而换到右边 |
| 读码就绪/设备旧状态已失效 | 每位标题旁“相机：已连接/等待数据/断开/状态过期” | 相机连接状态与包裹业务结果分开，不用绿色“正常”概括所有层级 |
| 本次条码 / 本次包裹号 | 当前包裹号（字符串、保留前导零、可复制） | 不转数字；带采集时间/处理标识，避免上一件格口误读 |
| 目标格口 / 本次格口 | 当前格口（大字号、按内容长度适配） | 仅在本次有效响应后展示；等待/处理中/未知/失效不可沿用上次格口 |
| 作业详情 / 查看详情 / 观察、原作业与原因详情 | 当前包裹详情 | 首先过程、结果解释与适用下一步；GUID、技术码、原文在技术详情 |
| 最新观察 / 原码 / 观察来源 / 关联原作业 / 原因 | 详情→技术详情 | 保留追溯能力；按所选包裹固定，不随新包切换 |
| 暂停新入场 / 恢复新入场 | 作业更多→暂停接收新包 / 恢复接收新包；仅相关状态显示适用动作 | 需核实后端真实定义，不意味着PLC停机或安全急停；维护应用流程可引用既有能力，不新增正常每包步骤 |
| 核对原请求 / 核对所选原请求 | 异常详情→核对WCS原请求结果 | 固定包裹和原请求；只读查询是否支持需后端核实；绝不默认重发业务 |
| 继续原阶段 / 继续所选未尝试阶段 | 异常详情→继续未执行步骤，并写明下一阶段 | 仅后端能证明未曾尝试且允许继续时显示；非通用重试、非重新入场 |
| 选择此位为命令目标 / 全局left下拉 | 移除独立的全局命令目标选择 | 通过明确包裹的详情执行命令；执行前显示左/右、包裹号，防止目标漂移 |
| 操作员登录 / 账号 / 验证身份 / 登出 | 启用登录组件时的身份入口 | 不新增强制登录；第二输入用途待验证；认证成功不自动清除维护阻断 |
| 显式参考输入 | 设置/诊断→模拟调试（明确模拟模式） | 真实生产入口不展示模拟注入按钮；不连接真实设备 |
| 辅助窗口 | 视图→第二屏作业（仅证实有需求时保留） | 与作业复用一套结果表达；只读/可操作性需确认 |
| 紧凑布局 / 经典兼容工作台 | 同一UI的响应式尺寸策略 | 若经典页无独有能力则取消独立入口；能力迁移与后端确认后再删旧实现 |
| 完整条码（保留前导零） | 记录→包裹号文本框 | 按字符串搜索；精确/模糊支持以实现为准，不在设计中虚构 |
| 投递位（留空表示全部） | 记录→位置下拉：全部、左、右 | 由当前Application的站位清单提供，减少手输入错 |
| 业务状态 | 记录→结果下拉 | 枚举由Application提供，显示用户可理解文本 |
| 原请求ID | 记录→高级筛选→原请求ID | 仍可精确定位；不占常用筛选行 |
| 开始(含)、结束(不含) | 日期时间范围组件，解释边界 | 同一时区展示并清楚标记；保留底层精确边界，不能悄悄改成双闭区间 |
| 日期 / 时间 / UTC偏移 | 常规组合日期时间；时区单独说明，高级可看原文偏移 | 不默认按本机时区隐式改写；无效日期、时间、偏移分别就地校验 |
| 今天 / 最近24小时 / 不限时间 / 清除 | 记录日期快捷筛选与“清除时间条件” | “清除”只清此范围，不清作业数据 |
| 高级精确时间原文（含UTC偏移） | 记录→高级筛选→精确时间输入 | 接受格式需要源码核实；给带偏移示例并显式标示例 |

| 导出当前筛选CSV / 取消导出 | 导出筛选结果 / 取消导出 | 导出字段、行数、敏感字段范围预览；取消仅取消该导出，不取消业务 |
| 观察时间/UTC偏移 | 记录表格→发生时间；列头说明现场时区 | 原始时间与偏移在详情保留，不能丢失追溯语义 |

## 4. 建议的新任务流程

### 操作员：连续供包

任务目标：确认当前工位可接收，在左右位置连续读取本包结果。

入口：软件启动后直接进入作业；未完成首配时显示明确的配置状态及首配入口。

步骤：查看工位身份、当前接收能力和两路连接状态 → 相机自动读入左/右包裹 → 该侧即时进入“查询格口”，清出上一个格口的主显示区 → WCS返回有效结果后只更新相应侧 → 操作员按实际现场流程处理，不增加每包确认。

成功反馈：固定位置显示本次包裹号、格口、结果时间；“取得格口”只代表收到WCS结果，不宣称实体包裹已经完成。

失败处理：当前卡片显示原因及适用动作，未知结果引导核对原请求；不因一侧异常擅自宣告另一侧能继续或必须停止，影响由应用运行状态给出。

返回作业：诊断或记录退出后保留当前实时左右状态，历史详情继续保持固定对象直至关闭。

### 调试人员：检查配置完成状态

目标：首次建立工位、设备实例、站位绑定及WCS服务，并知道是否真的已运行。

入口：首次配置向导；后续进入设置指定对象，不重走向导。

步骤：明确当前Application → 工位身份 → 选择已交付驱动 → 新建设备实例 → 按稳定设备身份绑定左右位置 → 配WCS实例 → 分层检查 → 查看变更与生效方式 → 保存/应用。

成功反馈：已保存版本与正在运行版本一致；每个测试层级分别有证据。连接成功不等于业务请求已通过；模拟原型不代表真实设备已验收。

失败处理：保留其他输入，定位出错对象与字段；未完成草稿不冒充有效配置；应用失败显示仍在运行的版本或“运行状态待确认”。

返回作业：配置成功/保存稍后应用后都可返回，但作业页持续显示是否可接收新包。

### 维护人员：处理WCS异常

目标：判断是连通性、设备/服务会话、响应内容还是结果不确定，避免盲目重发。

入口：作业异常条→查看诊断，自动带入受影响对象与包裹。

步骤：查看影响范围和最后有效状态 → 分层检查地址/端口、协议连接、数据/响应语义 → 定位到相应配置字段或外部故障 → 在适用情况下修改并等待安全时机应用 → 恢复后读回运行状态 → 对结果未知的原包单独核对。

成功反馈：连接恢复、业务响应验证、运行版本、原包结果分别陈述。网络恢复不能自动把未知包改为成功。

失败处理：保留原包身份和已输入配置，可复制脱敏技术详情、导出本地诊断摘要；不自动保存/应用、不发送生产业务测试。

返回作业：清楚显示仍未解除的限制；“已阅警报”与“故障恢复”和“原包核对”是三个不同事件。

## 5. 主要按钮行为契约

| 新按钮 | 作用对象与启用条件 | 执行中反馈 | 成功结果 | 失败处理 |
|---|---|---|---|---|

## 6. 六项原型走查与真实验收分开

以下是应执行的断言，不是已通过记录。实际通过结果由原型运行记录写入，不可把本表当已验收证据。

| 场景 | 可点击原型需要证明 | Windows/真实链路另行验证 |
|---|---|---|
| 1 左右连续处理 | 左侧模拟新扫码后主格口清空进入处理中，右侧成功结果不变；乱序模拟返回仍对应各自包裹；历史详情固定对象；不出现每包确认 | 相机SDK事件、并发/乱序请求关联、生命周期边界、UI线程更新、真实扫码持续负载 |

## 7. 不能由截图确认、应集中核实的少量事项

1. 目标工控机有效客户区、DPI、现场观看距离与键鼠/触控方式；附件像素尺寸不能直接当作逻辑尺寸。
2. 每一Application的实际身份/称重/传图适用性；截图里的登录阻断是合成场景，不能据此要求Sportmaster永久强制登录。
3. 当前包结果何时过期、旧包何时移入历史、WCS“未知结果”核对接口和可继续阶段的实际能力。
4. “暂停新入场”真实范围、在途包处理与恢复条件；相机仍读码不等于客户端仍接受新业务。
5. 支持预览“固定5分钟”的确切含义、最多7天约束、默认脱敏范围；未提供的站位诊断弹窗只能作为新设计和实现依赖。

没有用截图推断性能、点击耗时或效率提升百分比；改进体现在可见的信息定位、对象确认、状态解释和任务切换减少。
