# 有证据的问题与交付门槛

编号统一为 **LIA01-F01～F09**（下文简写Fxx）。严重程度S1/S2/S3表示后果，不表示证据强弱。“高”表示所述源码/展示事实可直接定位；人的误解概率及现场后果仍需观察。源码推演步骤并非声称已注入故障。所有生产、安装、系统与设备动作本轮只读。

## F01 卸载结果丢弃“保留残件”状态

- **角色/任务/前置：** 实施维护完成卸载；程序目录有不属于原清单的附加文件，或空目录清理无法完成但不需要重启。
- **复现路径（源码）：** 原目录放入非清单文件 → 正常卸载原清单 → `CleanRemovalInventory`保留非空目录 → 回执为`RemovedWithRetainedFiles`且`RestartRequired=false` → 结果窗。
- **预期：** 明确区分程序登记已移除、原数据按设计保留、额外残件保留；列出原因/路径与安全下一步。不得擅删额外文件。
- **实际：** 回执有`Status/Retained`，但构造和按钮回调仅传`RestartRequired/OperationFile/DataRoot`；false分支显示“卸载操作已完成”，没有展示残件清单。
- **证据：** S03:18/37/61–69；S04:75–77/108–119。**源码可确认，高；原生卸载未执行。**
- **后果/程度：** S2。维护可能以为程序目录完全清理，交付/重装核对失真；没有证据表明原数据被删除。
- **根因：** 平台返回多状态事实，展示层压缩成一个布尔值；“按设计保留”与“未完成清理”未分开。
- **建议：** 展示完整回执，区分三类终态及保留项类别；可复制/定位原回执，终态不重新要求已经移除的管理服务授权。
- **验收：** 隔离安装分别验证干净移除、额外非清单文件、文件占用需重启；窗口与原回执逐项一致，非清单文件和共享驱动保留，重启前后措辞准确。对应WP-LIA-01。

## F02 卸载已退役后没有可发现的固定清单续办入口

- **角色/任务/前置：** 实施维护；已写退役登记但文件清理/回执末次写入中断，或Windows重启清理后需确认。
- **复现路径（源码）：** 在S04先退役后清理的边界中断 → 重开产品维护窗 → `LifecycleState != Installed`直接到结果页 → 找继续清理/核对入口；再从同源完整介质打开安装向导。
- **预期：** 可读取原清单状态，识别残件/重启条件，用原介质和合法权限继续同一清单；不重复业务维护、不猜路径递归删。
- **实际：** 结果页仅“关闭”；安装向导未调用`ResumeRemovalAsync`。全src检索该方法只有Assembly定义/内部命令分派。运维指南却描述存在“继续退役程序的中断清理”入口。
- **证据：** S02:100–105/237附近；S03:47/61–70；S01；S13:75。**源码可确认，高；中断卸载原生验证待执行。**
- **后果/程度：** S1。系统项/快捷方式可能已移除，普通使用者失去正常重入路径；只能求助源码级维护。此处不意味着平台没有续办能力。
- **根因：** 原操作恢复能力没有接到现行人工入口，文档仍沿用旧入口承诺。
- **建议：** 同源介质识别退役登记并提供“核对原卸载/继续剩余清理”；绑定原SourceCommit、登记hash和受保护清单，显示当前状态、可执行条件及原数据保留位置。保留不需要管理模式再授权的终态修复。
- **验收：** 在退役前、退役后/清理前、部分清理后、终态写回前分别中断；重入只续原清单，错误介质/改过清单被拒，业务不启动。包括原EXE已不存在时的完整介质入口和Windows重启后核对。对应WP-LIA-01。

## F03 安装结果未知后让用户解释记录目录

- **角色/任务/前置：** 实施人员；UAC helper可能已提交，但等待超时、通道中断或回执无法确认。
- **复现路径（源码）：** helper仍在执行/已提交 → 触发`InstallationOutcomeUnknownException` → 向导显示“安装结果待确认” → 主按钮“打开安装记录目录”。
- **预期：** 软件绑定本次操作，给出只读核对动作及可理解的结果；仍未知时说清需带走哪份证据、由谁处理，不能重放提交。
- **实际：** 正确隐藏下一步并警告勿重复安装、关窗不取消；但点击仅启动Explorer，没把受保护登记/原回执核对转成用户可读结果。
- **证据：** S01:109–129/207–223/262；S02:353–406。**源码可确认，高；等待与故障UI未在本轮注入。**
- **后果/程度：** S1。安装到首配关键衔接停住；不知道源码/回执结构的人不能可靠决定等待、启动、修复还是重新安装。
- **根因：** 将正确的“不盲重试”守卫当作恢复流程的终点；诊断目录代替了产品任务。
- **建议：** 固定原操作身份，只读核对合法记录；区分进行中、已提交完整、系统投影待修复、未提交失败、仍未知。不能仅因发现目录就宣称成功。关闭后由同一介质/登记找回原操作；保留手动打开记录作为辅助。
- **验收：** 覆盖未授权、明确未提交失败、提交前/后断管、超时后成功、回执不可读；重复点击不重复安装，核对不能调用安装命令；无可信证据仍保持Unknown。验证键盘焦点和终态下一步。对应WP-LIA-01。

## F04 参数“已保存”到“已生效”需要用户自行拼接流程

- **角色/任务/前置：** 管理模式人员，已暂停、合法审阅并提交一份需要重启的完整候选。
- **复现：** 日常参数页 → 保存更改 → 得到PendingRestart → 尝试从结果窗口完成应用及确认运行值。
- **预期：** 知道正在运行的修订、待应用修订和停止影响；能选择稍后或进入受控应用流程，最后核对Effective和连接/准入条件。
- **实际：** 正确说明保存不代表运行；保存按钮隐去后提供返回/原保存核对，没有运行内应用路径。高级工具可查看运行与Pending原文；正常退出再启动能触发应用，但“怎样受控退出、从何重开、怎样验结果”仍由人员推断。重连只用运行配置。
- **证据：** S05、S06；`ParameterRuntimePresentation.cs`与`ParameterSettingsControl.Capabilities.cs`的待配置/重连提示。**源码可确认，高；独立完成困难为专家推断，未测用户失败率。**
- **后果/程度：** S2。易把保存或重连当作应用完成，延长停机、反复编辑；Application目前保留旧运行配置，未发现静默越过守卫。
- **根因：** 编辑提交任务与启动生命周期任务各自正确，但没有面向人的连接。
- **建议：** 保存结果展示修订摘要、影响和“稍后应用/检查并退出”；复用现有StopOwner、草稿守卫及启动分类，重新启动后主动显示有效修订/失败原因和待配置能力。离线“保存并启动”与运行内应用共享状态解释。
- **验收：** 原目标A→候选B；保存后A继续有效，受控关闭/启动成功才B；失败保留可核验状态；未知原请求仍固定A；授权到期保留输入；阻断时给可执行解除步骤；不自动Resume。对应WP-LIA-02。

## F05 已编辑历史条件与列表“查询完成”反馈不一致

- **角色/任务/前置：** 操作员或维护已查到记录，准备改条件继续核对/导出。
- **复现：** 查询非空列表 → 在“完整条码”输入不同值，不点击查询 → 看状态行和原记录。N03实际将空条件改成`NO-MATCH-SYNTHETIC`。
- **预期：** 立即提示“条件已修改，当前列表仍属于上次查询”，可辨认已应用条件；下一页/导出解释为何暂不可用。
- **实际：** 字段多数为auto-property，时间仅通知自身，状态仍“已读取8条作业 · 查询完成…”。清空筛选反而有明确旧范围提示。生产路径在翻页/导出时有签名守卫，不能据此声称会导出错误文件。
- **证据：** S07:9–22/44–48；S08:71–91；N03的`05-history-after-input-timeout.png`。**源码高，同源原生展示可复现。** UIA set_value报告超时后截图已显示新输入，未盲重试；后续查询用的是夹具fallback，不用于判定生产过滤逻辑。
- **后果/程度：** S2。用户可能把旧结果当作新条件结果，错误认定存在/不存在某作业，或到导出时才返工。
- **根因：** 已应用查询和正在编辑的条件有内部签名，但未成为可见状态。
- **建议：** 统一字段变更通知，显示新条件未应用及已应用范围摘要；可保留旧行供比较，但明确归属；动作状态与应用签名一致。
- **验收：** 每类条件编辑、清空、时间快捷项、查询期间再编辑、失败重试、取消导出均准确表示范围；使用真正实现IParcelHistoryApplication的原生壳验证导出/翻页，不用缺接口proxy代替。对应WP-LIA-03。

## F06 投递位查询要求用户知道内部标识

- **角色/任务/前置：** 操作员按主屏“左/右投递位”查历史，站点实际PositionId为`left/right`。
- **复现路径：** 作业记录 → 投递位输入“左投递位” → 查询；后端以原样字符串精确匹配。原生列表本轮实际显示left/right。
- **预期：** 从该站实际对象中选择左/右或实例名称，必要时展开稳定标识用于技术核对；不用靠记忆抄内部ID。
- **实际：** 自由TextBox只提示“留空表示全部”；HistoryFilter原样传Position，SQL比较`h.position=$position`，输入中文不会映射。没有“该投递位不存在”的业务选择提示。
- **证据：** S09:9/23；S07:29–39；S10:34–51；N03列表。**源码高，内部标识显示原生已见；中文筛选生产运行未执行。**
- **后果/程度：** S2。可能误以为该侧无记录，产生跨侧找数据和重复查询。
- **根因：** 查询端暴露技术键，未复用业务对象名称/实例映射。
- **建议/验收：** 选择项包含“全部”、当前/历史有效投递位可辨认名称及稳定ID；多实例/停用历史位仍可查。验证左右同码不同实体、历史已删角色、大小写/空白行为；不修改存储原ID。对应WP-LIA-03。

## F07 历史记录只有下一页，跨页比较要重新开始

- **角色/任务/前置：** 查询结果超过一页，用户需要返回刚看过的一页核对原请求。
- **复现路径（源码）：** 查询 → 下一页 → 寻找上一页/返回本范围首屏；只能重查并再次向后浏览。
- **预期：** 同一固定范围可以前后导航，保留选中原作业与位置。
- **实际：** 只有`nextHistory`及下一页按钮，没有游标栈/上一页入口。重新查询会重新固定上界，不能保证还是同一快照。
- **证据：** S08:71–99；S09:5。**源码高；本轮仅8条，未执行跨页原生验证。**
- **后果/程度：** S3。反复查找增加负担，数据增长时更难比较；不是错误重发或历史丢失。
- **建议/验收：** 复用固定选择保存页游标栈，增加上一页/返回本次第一页；筛选改变明确重建查询。用三页合成数据、查询后新入场和跨页选中详情验证，无需新增独立分页框架。对应WP-LIA-03。

## F08 主窗X与暂停、辅助窗关闭的影响缺少作业摘要

- **角色/任务/前置：** 操作员准备交班/离开，存在未决责任或待生效设置；没有未保存编辑。
- **复现路径（源码）：** 主窗X → 界面排空 → 没有dirty editor时直接StopOwner；对比辅助窗X（无StopOwner）及暂停按钮。
- **预期：** 对确有未决责任/多窗/待生效的根退出，能预知停止影响、需交接对象和再次打开位置；避免误以为只关闭一个页面。
- **实际：** 关闭守卫关注未保存编辑和资源释放，没有先展示未决作业/待应用修订的停止摘要。停止失败会明确保留资源，这一保护应继承。
- **证据：** S06:130–166；N03合成无草稿窗口关闭（无真实StopOwner）。**源码高；人因风险为专家推断，正式客户端关闭待验证。**
- **后果/程度：** S2。可能意外停止整个工作站/丢失交接上下文；未确认发生业务数据丢失，不要求阻止所有安全退出。
- **建议：** 与F04共用根退出预检摘要；对有影响场景给“继续工作/检查并退出”，解释软件暂停与停止；普通辅助窗关闭保持轻量。未决请求保留，不能要求用户靠重发来“清空后退出”。
- **验收：** 空闲、未决原请求、Pending、多窗脏输入、关闭期间收到回执、停止失败；选择取消不改业务，确认停止按现有owner机制释放，重开不重发。对应WP-LIA-02。

## F09 现行操作说明混用旧入口和多个当前版本

- **角色/任务/前置：** 不读源码的实施维护人员，沿INDEX进入安装/维护指南。
- **复现：** 阅读INDEX“当前”版本 → 按commercial operations安装2–4步寻找运行账户/站号/模式/信任包选择 → 卸载中断后按第75行寻找继续清理。
- **预期：** 当前版本、当前交付和历史回执各有一个明确入口；指南中的动作可在对应版本实际找到。
- **实际：** “当前”同时出现SM1.11.0、1.11.1及运维指南1.12.0；main1.12.3。现行向导默认新部署UsersSid、Production种子并从介质选择离线包，仅显示目录/快捷方式等正常选项；清理入口缺失见F02。
- **证据：** S01:281–300；S13；[GD01–GD07](baseline-and-guidance.md)。**文档/源码高。**
- **后果/程度：** S2。人员寻找不存在的控件、混用介质、把历史测试当当前保证；属于维护任务障碍。
- **根因：** 增量文档在顶部叠加“当前”提示，没有维护稳定的现行操作入口和历史适用范围。
- **建议/验收：** 保留历史原件，重建一份当前岗位指南和交付身份表；对照本版原生窗口逐步验证正常/失败入口；实现缺口明确标“未提供”，不得先写“已可操作”。对应WP-LIA-04。

## G01 真实RCS未知结果的闭环仍依赖外部合同

**这是交付门槛，不把缺失合同包装成可自行实现的按钮。** Sportmaster当前签名模块不支持权威查询，`QueryAsync`返回null；Unknown不能靠重复POST解除。主窗提示联系维护、不重复放货，应用保留原责任是正确保护。主要受影响任务是未知后继续供包、维护换配置、升级/恢复/卸载前的原责任核对。

源码可信度高（S11），真实对端处理事实和现场裁决流程未知。影响可达S1持续停机，但没有本轮现场发生频率证据。后续WP-LIA-05先完成原作业交接材料、禁用原因与可执行联系人/流程配置，再取得获授权真实查询/人工裁决合同及验证；不能编造SDK、客户规则、批准人、请求去重保证或自动重发策略。原D/CAPI/RV状态按实际证据另行更新。
