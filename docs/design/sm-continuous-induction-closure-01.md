## 1. 目标、非目标与术语

### 1.1 用户可观察目标

- **正常件零额外操作**：本位已就绪、当前 RCS 小车具有安全接单资格、设备正常、包裹有唯一可见合法条码时，操作工只需放件；软件放稳识码、校验、持久接纳、仅首次外呼 RCS，展示本次格口/异常。
- **异常件取下完成本件**：无码、非法码、多码、识读失败、超时以及无远端副作用的业务拒绝，操作工取下后由可信空盘自动完成轮次；视觉不可信时明确人工确认一次；如果远端调度安全，立即进入真实可投包状态，**原车号允许不变**。
- **快速连续上件**：前一件与后一件之间的可信空盘不足阈值时，RCS 心跳确认实际换车可独立推进；同码不同件不因文本相同漏报。
- **局部故障**：单侧相机/位置/外呼问题优先只影响本位。WPF 显示“真实可自动投”“只能人工输入”“等待新车”“请求待核对”等准确含义。

### 1.2 不承诺的事

- 相机无法看见、严重遮挡、不可解码的条码，不保证自动识别。
- 在**同车、两件之间无可信空盘、无可信换车、无其他独立物理证据**时，不能靠换码推断是不同包裹；需要有边界的人工明确操作或新增现场传感证据。
- HTTP 已发送而客户 RCS 是否接单未知时，不得为追求流畅向可能已占用的小车重复外呼。只有可证实安全时自动恢复。
- 不改客户 RCS 协议，不依赖不存在的远端查询、撤销、幂等保证；不在本轮实施自动更新/安装、DB 迁移或重构其他 Application。

### 1.3 必须分离的身份

| 身份 / 账本 | 定义 | 唯一性与生命周期 | 不允许的替代推断 |
|---|---|---|---|
| **物理包裹轮次** `RoundId` + `PlacementGeneration`（建议领域概念，可复用现有账） | 一次操作工放件、识读、处置及取件 | 可在同一小车连续形成多个；每轮最多一次业务提交 | 不由条码字符串定义，不由 UI 3 秒复位定义 |
| **实际到位车辆** `StationCode/BcrCode/AgvNo` + `ArrivalGeneration` | RCS 证实的本位小车 | A→B→A 为三次可信到位；同车异常重投不伪造新车 | 心跳 `requestId`、IDLE/TASKING、缺车号不等于换车 |
| **调度责任** `OperationId/RequestId` + T0/T1/T2/回执/目标状态 | 一个冻结的 RCS 取格口请求对哪辆车可能产生副作用 | 即使轮次结束、超时、进历史也持续保管直至能证明不再影响当前物理目标 | 本地取消、空盘、超时、HTTP200、历史归档都不能伪造无副作用 |
| **相机采集身份** `ReaderEpoch` + `CaptureBoundaryId` + `CaptureTicks` + 物理轮次和车号代次 | 确保候选是当前包裹/车辆的新帧 | 每次可信车辆切换、需要排空的物理轮次切换、相机重连都建立相应边界 | 解码完成时间不能替代曝光/采集时间 |
| **人工命令身份** `CommandId` + `RoundId/Version` + `PlacementGeneration/ArrivalGeneration` | 人工确认、PDA、键盘的目标冻结 | 原命令重放返回原结果，不重执行 | 未提交的旧输入不能借新轮次自动提交 |

**核心澄清**：“RCS 一车一件”约束成功分配/执行的车辆承载责任，不等价于“一辆尚未接单的车只能尝试识读一个包裹”。同车无外呼或可证明无副作用的多次失败尝试可以轮换，但每次是独立的包裹轮次与原请求身份。

## 2. 强制业务不变量（高于体验优化）

1. **同一轮次最多一次 `DispatchClaim` 和一次首次真实 RCS 外呼**；相机/PDA/键盘通过 Application + Repository 的原子序列化竞争。重复码/换码、重启、切页、超时、重新确认不能改变这一事实。
2. **无可信物理边界不创建新的自动轮次**。可靠空盘或可信换车是两种并列物理边界；同一物理变化的双事件只能生效一次。
3. **物理轮次结束不清除远端调度责任**。包括已开始写入请求、Unknown、仍可能迟到绑定、已成功接单但小车未走等。
4. **RCS 车辆未证实/成员版本不一致/实际目标不安全时禁止生产外呼**；可显示预览和受控草稿，不得假报已提交或缓存旧请求待恢复后自动发出。
5. **所有已发送请求保留原冻结 `requestId`、报文、目标、回包、原始结果及事件时间线**，不自动重发、不伪查询、不擅自清理原件。
6. **两侧隔离**：每侧独立物理轮次、车辆、远端目标围栏、相机边界和操作指令，HTTP 资源共享受有界公平控制；慢网络不锁住另一侧的状态机。
7. **状态必须真实**：“等待投包”意味着当前至少明确的一种准入渠道真实可用；自动不可用而 PDA 可用时明确标识。不能只清 UI 卡片却保持 Application 一直拒绝新件。
8. **失败可重启、可追踪**：每次边界变化、首次提交、首次外呼与回执收口持久化，SQLite WAL/FULL 原有恢复与备份语义不退化；不以常态高频写审计替代可信性。

## 3. 三个独立状态机

### 3.1 本地包裹轮次（`ParcelRound`）

| 状态 | 含义 | 进入条件 | 离开条件 |
|---|---|---|---|
| `Empty/Waiting` | 无当前包裹，等待上件 | 初始、可信离位完成、合法结束上一轮 | 可信在位或首次可用于业务判断的正式候选、人工完整输入 |
| `Reading` | 识读/纠正中 | 新物理轮次启动；此时冻结轮次身份 | 唯一合法码成功接纳、人工补录或取件；快速阶段到期可进入安全续读/补录等待 |
| `Admitted` | 原子取得一次生产提交权 | 合法码 + 全部业务与远端安全守卫 | 背景外呼、异常结果、可信取下或车辆切换；不授予第二次提交 |
| `Result/Exception` | 展示格口、业务拒绝/未确认/识读异常 | 原作业产生结果或识读阶段结束 | 可信取件、有效换车、必要的人工确认；显示时间到期仅清旧展示，不证明物理离位 |
| `Ended` | 当前包裹物理作业结束 | 合法边界证据或明确人工取下确认 | 只供历史；不会变成新的当前轮次 |

空车没有 `RoundId`，不启动读码期限。只有“全是底码”或无正式候选且没有可信上件时，不能制造超时或伪包裹。

### 3.2 本位车辆（`VehicleArrival`）

`Unconfirmed → Confirmed(A) → Confirmed(B)`；同车重复心跳只刷新合法有效期，不能新建代次。失联、无成员、无车号不能假造撤车；可取消当前自动准入，但保留最后已知车号及提交事实。断线恢复 A→A 不证明换过车；已可信观察到 A→B→A 则可分辨。

RCS 心跳的成员选择、串行请求、启停确认、相机编码映射和 `data:[]` 继续沿现行协议；心跳间隔与 HTTP 时间预算独立。默认 1000ms 串行心跳不能被宣传成严格每秒确认一次换车。

### 3.3 本车远端调度责任（`DispatchSafety`）

| 事实分类 | 车辆是否安全承接**新的**请求 | 必须保留的事实 |
|---|---|---|
| `NeverClaimed`：本车从未形成外呼责任 | 是，在本位及车辆有效的前提下 | 当前轮次、车辆代次 |
| `ClaimedNotAttempted`：已持久接纳，但 T2 尚未成立 | **先原子取消/确认未发**，安全收口后可以 | 原准备请求及取消理由、原身份 |
| `DefinitelyNotDelivered`：权威可证实正文未送达且远端无副作用 | 是，但须保证先前操作已停止且不会迟到 | 送达证据、收口结果 |
| `RejectedNoSideEffect`：客户协议明确证实拒绝未生成任务/未绑定车 | 取下后是 | 原拒绝原文、合同依据、轮次结束证据 |
| `AcceptedBound`：RCS 已接单/可能放车 | 否，直到可信下一车到位并证明旧责任不影响新车 | 原任务、格口、车号、请求 |
| `SentUnknown`/`MayLateBind`：外呼已开始但结果/目标未知 | 否，除非有权威独立证据证明新目标安全 | 原尝试、超时、未确认原因和按位恢复围栏 |
| `RejectedEffectUnspecified`：`success=false` 但客户未保证无副作用 | 默认否，不从文字推断无任务 | 原错误码、消息、回执和核对责任 |

**拒绝语义待核验**：当前 RCS 响应有 `success/code/msg`，但字段自身不证明车辆未被绑定。`NEED_UNPACK`、无格口、`noDestToExp` 等按客户合同分类；未取得无副作用证据时严格进入安全核对，而不是假定所有业务拒绝都能立即同车下一件。

## 4. 双证据分轮的精确定义

### 4.1 可信空盘（视觉分轮）

- 前提：本次相机会话有效、显式空托盘校准有效、空盘参考匹配当前车辆/连续性、帧号及采集单调时间可信；不会用曝光失效/底码/无码/画面变暗代替空盘。
- 当前运行参数：**至少 3 帧、连续空盘 800ms**。相邻有效帧间隔超过 500ms、丢帧、会话切换、失焦/曝光异常时，连续性重新确认。
- **触发效果**：结束当前已存在的物理轮次，写入 `TrustedEmptyRemoval`；为下一个包裹开放新的物理识读轮次，但**不变更 RCS 车号**。若上一轮无外呼/有无副作用确证，同车允许新一件自动请求；若已接单/结果未知，只允许轮次结束并显示等待新车/目标核对。
- 相机未校准或视觉不可靠时，不伪造空盘；为确实需要取件的当前轮提供绑定原 `RoundId + Version` 的一次人工确认。人工确认只证明操作员声明已取下，不证明 RCS 无副作用。
- 同一次稳定空盘只处理一次，后续重复 Absent 不创建多个代次；后续需存在新的真实在位/正式候选，才会新建包裹轮次。
- **避免错误归属**：物理轮次结束时建立软件交付/识别有效性栅栏；处理旧采集帧的完成回调不得作用于新轮。与 RCS 换车不同，是否需要 SDK 原始缓冲排空由真实采集链路决定，必须保证新的有效帧不继承旧轮，不能只靠改变内存标志。

### 4.2 可信 RCS 换车（车辆分轮）

- 前提：完整合法、未过期、与本位 `stationCode/bcrCode`、请求编号、成员版本和当前配置一致的心跳；`agvNo` 从已可信 A 改为 B。
- **触发效果**：结束旧轮次，登记新的 `ArrivalGeneration`，关闭旧帧接纳，执行实际 SDK/交付缓存边界，B 的新帧才可自动识读；即使空盘未达 800ms也允许 B 新件。
- 同码不同车允许；同码同车但无可信取件边界不允许自动重复。
- 车号变化并不能凭空证明旧 HTTP 请求已安全终止。只有客户确认的“先绑定旧车后放车”及当前未撤车、没有其他迟到绑定风险等证据满足时，才能认定新车目标安全；否则保留局部围栏。

### 4.3 两事件竞态、次序和幂等

- **空盘先于换车**：先结束旧包裹；如果后续 B 到位，则更新到位代次和相机边界，不能因为已结束就忽略换车，也不能二次结束同轮。
- **换车先于空盘**：先结束旧包裹，切换到 B；晚到的 A 空盘帧按旧身份丢弃；B 当前有效空盘只证明 B 为空，不关闭任何后来开始的新件。
- **人工确认和视觉空盘同时到达**：只有绑定当前轮次且首次合法的动作能生效，另一动作返回已完成/过期，不清新轮。
- **PDA 回车、自动识码、车辆切换、原图保存或 RCS 晚回包竞态**：Application 的统一准入序列化 + Repository 原子事务决定归属。所有发送前再次核验代次和责任；既有外呼按原报文收口，不把结果投给新轮。
- **空盘短于阈值且车号未变**：没有自动分轮依据。文字变化、场景运动、底码或双扫不能创建新包裹身份；确实需要连续操作时提供明确的人工边界确认，前提是远端安全。

## 5. 完整投包链路与识读策略

### 5.1 正常链路（无需操作工确认）

`本位真实可自动投 → 可信包裹/正式候选 → 放稳识码 → 原始候选完整性校验 → 排除底码、整串允许规则与多码判定 → 唯一合法码 → 代次/相机/车辆/外呼准入最终复核 → 原子生成且占有唯一提交权 → 非阻塞异步外呼 → 原回执落盘 → 同轮 UI 显示格口`。

- 新站默认 MVID 原生识码；保留软件识码路线，不能两套识码同时占用同一相机。相机默认放稳 `200ms`，持续运动约 `1500ms` 兜底识别，两者均属于实际耗时和可靠性设计。
- 同帧两个真实有效码、候选不完整/正则超时、同码两个独立物理标签不能错误选择；排除固定车底码后只剩唯一合法码才自动提交。未被完整证据解释的候选保留诊断。
- RCS 离线/身份未确认期间可保持预览、人工草稿与可诊断的候选事实，但**不缓存过期扫码在网络恢复后盲发**。只有重新取得当前车辆和当前包裹的新鲜身份、且从未外呼时，才允许按新鲜证据提交。

### 5.2 识读 1000ms 的目标语义（需要重构现有硬截止）

默认 `1000ms` 到期保留本轮 `AutoExpired` 事实；**1000ms 优先完成快速识读**，并按下述证据决定安全续读，不永久拒绝仍可可靠证明在原位的正确件。

- **快速阶段**：原默认 1000ms 作为自动识读响应目标，包含放稳、候选处理、入队和准入前检查；不得每帧重置。已在原期限内完成真实采集及合法候选的事件，不应仅因内部排队过慢而被当作新件或永久丢失；必须有过期来源上限和当时及最终身份双重核验。
- **安全续读阶段**：本轮未提交、相机健康、车辆确认、原包裹可被可靠且连续证明在位、没有可信离位/疑似身份替换或帧连续性破坏时，采用有界/降频识别继续获取唯一合法码，成功则同轮自动请求；操作工仍可补录/取件。持续运动的兜底机会不应与 1000ms 截止互相抵消。
- **无法证明仍为原件**：没有视觉在位证据、发生丢帧/遮挡/重新上件疑似变化、相机重连或车号变更时，禁止把晚到条码当作原包裹自动外呼；只允许明确补录、新的物理边界或有效新车的全新识读。存在视觉无法证明“没有在 800ms 内调包”的本质限制，不能宣称相机可绝对识别同车短间隔换件。
- 续读不能无限写每帧 SQLite、无限积压日志、原图和执行任务；必须限制重复识别的工作量、补录/取件并发、错误预算，并保留每个最终决策的可追溯证据。

### 5.3 业务受理与发送阶段

- `T0`：识读候选；`T1`：持久接纳并占位；`资源等待`：不代表发送；`T2`：持久登记真实首次尝试；`HTTP/Body`：可能远端见到；`T3`：原回包完整归档。T1→T2 被可信取件/换车结束且确证未外呼时，本地取消；T2 后不得假设取消，原请求按冻结身份收口。
- “合法包裹自动请求”仅在设备/RCS、当前车辆/调度责任、安全性、存储/资源全部可用时成立。RCS 业务拒绝、超时/Unknown、实际容量耗尽是可审计的非成功结果，不是假扫码成功。
- 取格口 API 保持现行 `SPORTMASTER-RCS-SORTER-v1` 报文，唯一 `StationCode` + 每位 `BcrCode`，不改外部参数/源标识；底层 HTTP 限流、左右公平和心跳独立池保持有效。

## 6. 异常件“取下即结束”完整规则

1. **尚未正式识码/未发送**：有当前 `RoundId` 时，可信空盘结束轮次，下一件同车可用；未形成 RoundId（未见包裹也无候选）本来就在等待，不制造空任务。视觉不可靠时明确操作工取下确认；不要求停用再启用。
2. **多个码/非法码/识读超时**：操作工可继续调整、PDA 补录或取下；可信取下后，当前未发送责任安全收口，真实准入可用才显示等待。
3. **合法码已 T1 未 T2**：结束物理轮次时先在同一事务安全取消尚未尝试的原请求及发送排队，确保未来零迟到外呼；原准备证据保留。完成后同车下一件可用。
4. **RCS 明确拒绝**：若客户 RCS 合同证明无任务、无绑定、无未来副作用，取下后同车继续；否则结束轮次但本车待核对，不让操作工误认绿灯已可投。
5. **RCS 成功接单**：本轮只能完成展示/物理离位；同车不可二次发送，必须等待可信下一车且原责任不会误绑定新车。
6. **T2 后 Unknown/不确定**：本地轮次取下即完成，但远端责任独立保留、只围住相关位；不得让操作工快速启停、反复 PDA、重新投同码绕过。外部确认后按原安全操作恢复；历史 Unknown 如已不可能影响当前目标，不得永久充当前位容量占用。
7. **手动确认取下**：只对当前轮次有效、一次幂等、包含操作身份/时间/原因，不改变原外呼结果，不免除对 RCS 小车身份与调度责任检查。可靠视觉已经确认时自动完成，不重复要求点击。
8. **操作员重新放同一包裹**：若新可信物理轮次成立且原件从未外呼/已证实无副作用，可以重新识读并产生新唯一 Operation；如果已成功接单则禁止再向同车发送。

## 8. HMI / 操作工交互契约

- **等待投包**：必须有真实可提交资格，不得仅根据轮次已结束显示。相机不可用但 PDA 可用时显示“相机不可用，可人工扫码”，不得冒充自动可用。
- **识读中**：条码候选及当前包裹，放稳/纠正操作直观；不依赖无意义确认按钮。
- **识读异常、请取下包裹**：显示准确原因（无码、非法码、多码、超时、RCS明确拒绝等）与可选补录/取下动作。可靠空盘自动结束；视觉不可靠才提供本轮取下确认。
- **正在取格口**：显示已持久接纳与正在外呼的不同阶段；真实结果未到不能显示成功。
- **已取得格口**：格口、条码、任务信息只来自当前 `RoundId`；旧轮一旦结束撤去旧格口，结果可在记录查看。UI 展示 3 秒不决定物理身份或接单权。
- **等待下一车**：本车已被 RCS 接单，需新车才能继续外呼。即使托盘视觉空着也不误报可投。
- **请求待核对**：局部红/灰阻断，说明原请求/车辆责任；操作工不能通过连续点击停用启用强行清围栏；给维护人员证据入口。
- 状态、卡片、按钮、PDA 输入均绑定当前位/轮次/版本/车辆代次；旧回包、图片、计时器和输入不得覆盖新件。左右 UI 不交叉。

## 9. 数据库、日志、可观测性和性能

- 基于现有 `SmPositionCycle`、`SmParcelRound`、`ParcelOperation`、`parcel_audit`、输入台账和原请求台账**收敛实现**，不机械新增三个表。必要时增加可核对的物理代次与远端责任字段，按当前格式变更规则处理，不做静默旧格式迁移。
- 一次事务内维护：当前轮次关闭/开启、外呼提交权、未尝试请求取消、目标状态变化和命令回执；在 T2 前再次核验，不把多个分散提交伪装成一次原子事件。
- 每轮关联：本位、车辆、`ArrivalGeneration/PlacementGeneration/RoundId/OperationId/RequestId`、条码候选及决策、可信物理事件、采集 `Epoch/Boundary/CaptureTicks`、首次提交、T2、原 HTTP 完整回执、格口及结束原因。关键事件要可检索复盘。
- 记录 `可信上件/首正式候选→识码→筛选→T1→排队等待→T2→RCS回应` 的真实单调时间，报告 P50/P95/P99 及异常样本；区分“已识码”“已接纳”“已实际尝试”“RCS已接单”。不得相加阶段 P95 当端到端时间。
- 重点指标：有资格合法件自动接纳/实际外呼比率、未发送分原因、同轮重复外呼数量、同码连续漏报、取件至真实可投等待时长、取件误判率、换车到首张可识读帧、左右输入积压、RCS响应分位数、24h SQLite/audit/WAL 增长与资源趋势。
- 现行心跳每轮每位多次 `StoreSmCycle` 提交，即便车辆不变也产生审计，调高频率前应实现有界的周期状态/关键变更持久化方案，兼顾崩溃期间的成员/外呼不确定性，不能仅为降低写入而丢责任。
- 当前 `800ms` 视觉移出门槛**先保留**；用独立标注的原始 Mono8 帧（时间/帧号/曝光/物理真值）比较 `500ms` 与 `800ms` 的误判、漏判及真实响应收益；只有证据充分才考虑将运行移出阈值改为 500ms。**校准参考所需 800ms 为独立保护，不随移出阈值一起改变**。

## 13. 本次实现与本机验证（2026-11-13）

### 实现落点

- `ParcelSmRounds` 在同一事务结束本件、取消零尝试请求及释放安全提交权；T2之后保留原执行、回执和目标责任。可靠空盘不再受人工来源或 RequireRemoval 阻挡。接单同车继续防重；明确拒绝但副作用不明时保留目标围栏。
- `SmPositionCycle.Generation` 仍表示车辆到位；`PlacementGeneration` 是同车物理结束的独立随机标识，随真实事件持久化。原 DB14 中尚未分开物理轮次的记录使用原 Generation 表示初始边界，读取不补写、不改原哈希。人工命令/WPF 草稿同时绑定车辆、物理边界和当前轮次；墙上时间重复不复用输入资格。
- 空盘与换车共用原 SDK/解码/交付清理边界，新 BoundaryId 退休旧帧，不重建相机所有者。空盘保持原车号和显式校准参考；换车清除该车在位累计。两种采集路线均传递捕获时的连续在位起点，丢帧、曝光失效、重连或中断后的新 Present 不续原件资格。
- 1000ms 快速窗口仍单次到期并可查询。过期后只接受原窗口内完成解码且仍在来源年龄上限内的事件，或具有捕获时/最终连续在位证据的同件续读。续读识别最小间隔500ms；MVID间隔内只取预览。原图保留后、T1之前再次核验，不把排队或图片写入当新窗口。
