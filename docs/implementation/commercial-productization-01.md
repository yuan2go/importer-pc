## 3. 数据权威、身份和权限

### 3.1 每类记录只能有一个生效权威

|记录|所有者与持久化边界|读写规则|
|---|---|---|
|Application/发行身份|构建及发布清单|业务版本、SourceCommit、RID、契约指纹、文件集合与兼容声明成套；安装 UI 不修改包内身份|
|安装计划与操作回执|受保护部署机制|计划固定输入集合、目标目录、已有登记身份和操作者；回执记录阶段及部分完成事实，不证明业务可运行|
|机器账户/受信目录/扩展信任|受保护机器策略|安装或维护提升写入；运行账户读。运行参数不能覆盖机器根、信任或 SID|
|工位身份及有效配置|Application 的原配置修订账|保留原 `configuration.json` 权威；种子只提供初始输入，导入模板和首配草稿不能覆盖已有 Effective|
|编辑草稿/探测结果|界面及独立配置服务的非生效记录|可恢复未完成编辑，绑定来源版本和参数摘要；不被 runtime 直接消费，不成为第二部署账|
|作业、请求、回执、编号责任|原业务数据库和原件保管机制|保持 T1/T2/T3、永久身份、精确旧目标/合同/包引用；安装、模板、修复不能改写|
|展示偏好|每用户的界面设置|列宽、语言、布局等与业务配置分离；不包含流程、角色授权、设备映射或外部目标|

当前程序固定部署在 `%ProgramFiles%\ImporterPc\releases\...`；策略、受保护种子和位置登记在 `%ProgramData%\ImporterPc`；首次默认数据根为当前用户 `%LOCALAPPDATA%\ImporterPc\data`，已有安装读取原登记。本包保留程序/数据分离和旧路径兼容。自选路径是新增受支持能力，不能写成当前已支持。

### 3.2 账户与业务身份分开

日常运行必须是机器策略指定 SID，且实际未提权；UAC 过滤后的 deny-only 管理员组身份允许。错误 SID、已启用的管理员权限和系统/服务账户继续拒绝。所有直接 EXE、运行 API 和桌面入口在读取业务配置、创建锁/目录/数据库之前复用同一门禁，不只在启动脚本检查。

安装和离线写入通过明确的 Windows 维护授权执行；业务登录故障不得封死 OS 管理员的独立修复入口。操作员登录依 Application/产品配置决定，未启用时不造操作员身份；当前 Production 对维护认证的必要要求仍保留。Windows 管理员、业务操作员、维护权限、人工核对权限不是同一个角色，后端按具体命令重新验证权限和来源，不能相信 UI 传来的角色字符串。

敏感参数必须从表单、草稿、序列化、提权暂存、日志到导出一起设计。现有 `Sensitive`/PasswordBox 只是显示处理，不能据此宣称凭据已得到完整保护。新增秘密优先采用受保护引用；明确账户/机器作用域、权限、恢复与换机再配置规则。固定请求 hash 用于输入身份，仍需审核临时文件 ACL、通信对象身份、消息大小和日志脱敏，不把自带 hash 当操作者授权。

## 4. 安装实现：一次可审阅计划，明确的提交与恢复点

### 4.1 安装载体和部署内核

实施时根据已核验的 Windows 目标、离线依赖、修复/卸载和批量部署要求，选择成熟且受支持的 installer 工具；可保留既有 WPF 引导和受保护部署内核。选型形成简短 ADR，说明系统安装登记、升级身份、回执、重启续作与离线依赖如何落地。不要为套用某种安装文件格式重建一套与 `WindowsDeploymentSetup` 相互竞争的安装权威，也不要把新的图形 ZIP 解压器视为商业安装已完成。

系统“已安装的应用”信息与受保护部署登记必须有唯一产品身份和可恢复的一致性流程。为每个独立 Application 定义稳定安装身份及版本身份；单实例登记语义保持可解释。现有并排发布目录可继续复用，但不能出现系统卸载入口指向旧版本、运行快捷方式指向新版本、后台仍读取第三个数据根的分裂状态。

### 4.2 计划与执行阶段

1. **只读发现**：读取实际操作系统/RID、已有部署、机器策略、数据根、媒介清单和可选依赖。显示不支持条件、空间需求及是否重启；不启动业务或 SDK，不先创建空数据根掩盖旧部署。
2. **选择与核验**：用户选择程序根、保留或新建的数据根、已有 Windows 运行账户和本 Application 允许的组件。推荐值先给出，高级参数按需展开。升级预填原身份；身份冲突进入明确修复/迁移流程。
3. **冻结计划**：摘要固定 SourceCommit、媒介与组件 hash、精确包闭包、SID、路径、种子/模板身份、原登记 hash、所需系统变更和重启需求。用户返回修改后重新生成计划；执行时不能读取一个未复核的新地址或新文件。
4. **维护执行**：固定 helper 在受保护目录中重新验证计划及权限，取得安装租约和相关原应用所有权，复核原登记及输入。按顺序暂存/验证程序和允许的前置依赖；保留所有可恢复记录。
5. **提交登记**：程序、配置输入、权限、快捷方式和必要前置条件均达到该阶段要求后，提交唯一部署位置。若 installer 引擎还管理系统登记，明确其与应用登记的完成协议和中断恢复，不能假定跨组件天然原子。
6. **读回完成**：未提权界面从权威登记读回安装结果，显示真实程序/数据位置、组件结果和下一步。需要重新启动 Windows、切换运行账户或继续首配时分别显示；安装完成不能直接显示“生产就绪”。

当前实现以 `Prepared → ReadyToCommit → 部署登记提交` 保留旧版本，失败记录 `Failed`。扩展时继续保留最后提交点；每个可能中断的外部安装步骤有独立结果、重试资格与恢复策略。取消 UAC 不修改旧部署；取消下载/复制不得删除旧版本；执行已不可安全取消时说明当前阶段并完成一致的收尾。异常后从操作记录和实际文件重新核对，不能只根据上次 UI 进度继续。

### 4.3 自选程序根的完整保护链

当前 `MachineRuntimePolicy.RequireProtectedApplicationInstaller` 限定 Program Files/ImporterPc，`RequireProtectedEvidence` 限定 Program Files/ProgramData；因此不能只把安装窗口的路径硬编码换成文本框。新策略应在受保护机器策略中记录经维护批准的程序根，保留旧根兼容，并贯穿以下环节：

- 规范化路径，拒绝链接/重解析路径、危险嵌套、程序与运行数据互相包含，以及不满足本地卷与 ACL 要求的位置；检查祖先目录的写入/替换权限。
- 发布目录由维护主体拥有，指定运行账户只有所需读/执行权限；每个受保护 helper、依赖和证据文件均重新核验，不能从普通用户可写目录提权执行。
- 安装注册、快捷方式、启动参数默认值、证据验证、repair、升级、卸载和历史版本引用全部解析同一受信记录；运行中不靠 cwd 或环境变量改道。
- 迁移程序位置保留旧部署及回退入口；数据位置不随程序根改变。已有租约、政策和未决责任不由路径迁移自动清除。

### 4.4 驱动/组件前置条件

相机系统驱动或厂商 SDK 与本软件的驱动适配器是不同安装对象。RCS 集成包也不是 RCS 服务端。向导按本次允许的分发清单显示名称、作用、版本/RID、体积、必需/可选及当前状态；自动解决已批准依赖，不扫描目录后全部加载。

系统驱动/SDK 只在获得资料、分发许可和受支持安装方式时进入流程。对获准厂商安装器固定身份、来源、参数、检测规则、退出结果、重启需求及恢复方式；提权安装只执行显式批准的前置动作，不执行扩展模块代码。未取得实际安装合同的项明确“需要外部安装/待资格”，完成不受影响部分。签名包安装、厂商依赖存在、精确部署资格、实例配置、资源启动和业务准入分别出具状态，任何一步不能替代另一部。

## 5. 首次配置与组件配置

### 5.1 独立于业务启动的入口

首配服务与现有 `IStartupMaintenance` 一样不依赖 `IBusinessRuntime.Start`，读取声明和已有账即可进入。正常启动、安装完成页、开始菜单和启动失败页均导向同一首配/修复服务；不在各入口保存一份“是否首启”的全局布尔值。

根据实际状态路由：全新未配置部署进入首配；已有有效账进入运行或受控维护；已有草稿/Pending 展示继续编辑或待激活；配置损坏保留原件进入修复；恢复根保持隔离。工位或模式不匹配须明确选择原部署或新工位流程，不能通过填写不同站号跳过原数据。

新工位尚无原身份时，安装提供受信 Application/模板输入，客户可在独立草稿中配置站、设备及服务。草稿区绑定安装身份及来源版本，尚未成为运行配置；敏感字段受保护。首次提交在锁内检查真实已有目录、配置账、数据库、原件与部署记录，确认不存在被重新命名隐藏的原责任后才建立该工位的初始配置记录。一旦存在原身份，继续使用原 `RequireIdentity` 约束；变更站号、模式、Application 归迁移流程，不能放开通用编辑器来解决首配。

### 5.2 客户填写内容与模块声明

|步骤|用户操作|实现规则|
|---|---|---|
|站点与模板|新建或导入已批准模板，确认当前 Application/站/模式|模板只给配置意图；站与设备唯一身份、地址、凭据引用及 RCS 编号范围逐站确认，已有账不覆盖|
|组件使用|选择随包或已安装的受信读码驱动/RCS 等能力|只列本 Application 的已声明兼容选择；系统安装状态和启用状态分开；可选项不启用时跳过其专属参数|
|相机/读码器绑定|按可证明的稳定设备身份选择并绑定 left/right 或该 Application 的既定角色|不使用枚举顺序、窗口焦点或临时索引代替设备身份；未提供枚举能力可输入已核验标识，并显示“未验证”|
|服务参数|填写选中组件声明的地址及必要参数|由组件 schema 生成必填、范围、条件字段、说明和敏感输入；主向导不编造 SDK 属性或 RCS 协议|
|检查与保存|查看差异、缺项和验证层级，保存草稿或提交完整候选|校验结果对应精确参数/绑定 hash；修改后旧检查失效；保存、激活和就绪分别显示|
|受控启用|在权限、责任、资格和资源条件满足后启动所选部署|保留激活尝试身份和结果；失败保留原有效配置/草稿及原始错误，随时可回到独立维护|

现有 Sportmaster RCS 字段以 [RcsTaskOptions.cs](../../src/Ipc.Integrations.SportmasterRcs/RcsTaskOptions.cs)及已签名模块 schema 为准：目标、source/locale、zone/project、每位 station/bcr、quantity、条件性指定格口和 request-id 范围。不要把这些参数升级为所有 WCS/RCS 的通用必填规则；不要杜撰认证或查询接口。编号范围必须有跨站不重叠的外部分配依据，UI 只校验本地规则不能证明全局唯一。

### 5.3 校验分层与保存语义

建立明确的检查报告：配置结构/字段、精确包与依赖、系统前置条件、部署资格、真实连接/探测、业务准入。报告携带检查时间、范围、配置 hash、提供者身份和失效条件。连接暂不可用可以保留草稿，尚缺批准资格可以显示待补齐，不能要求连接或最终生产资格成功后才允许客户开始填写参数。

当前 `ParcelCapabilityFactory.Validate` 会校验精确配置 hash 的部署资格，`ParcelStartupMaintenance.ValidateAsync/StageAsync` 复用该严格入口。实施时应分开“可编辑/可保存草稿”“完整结构及包闭包已验证”“可提交 Pending”“可激活并启用”，不能为了让首配保存成功删掉 Production 校验。未完成或尚缺资格的数据只存在非生效草稿；可从草稿生成固定候选摘要用于取得、导入匹配资格，满足完整提交校验后才向原唯一配置账 Stage。激活仍重新检查精确资格、原责任和资源。资格与参数互相依赖的问题通过这一候选摘要/资格导入流程解决，不伪造资格、不把 UI 检查结果当独立批准。

设备枚举和连接探测属于显式短期维护会话：只使用已批准能力，取得相同设备排他控制，限制超时和结果数量，结束时完成 Stop/Dispose。默认探测不触发分拣任务、不写 PLC、不发送有副作用的 POST。无只读探测合同时显示“不支持独立探测”，不能拿真实发单试连。探测对象不得与运行实例重复占用；关闭窗口不提前释放尚未清理的原生资源。

### 5.4 必须解决的未确认配置循环

静态控制流发现：当前 `ParcelRuntime.StartAsync` 先准备 Effective 确认；只有 `Confirmation.Required != true` 才尝试 Pending，随后校验并启动当前 Effective。若初次 Effective 因错误配置始终无法启动，仅离线保存正确 Pending 仍可能重复尝试原配置。此项为**待复现/待修复差额**，不是已修复结论。

首配和启动修复必须提供 Application 拥有的显式处置路径：保留原配置字节、确认信息和失败尝试，在同一所有权锁内检查原实例已停止，并证明允许此次初始替换所需的业务、请求、接收原件、设备及外部副作用责任条件。只有该路径的明确条件成立，才尝试未确认配置的候选；全过程仍执行精确包/资格、资源启动和结果确认，失败保留旧事实。已有未决责任时继续走匹配原发布的核对/恢复，不直接清 `Confirmation.Required`，不把候选写成成功 Effective，不以“数据库是空的”替代完整责任检查。

验收必须覆盖“原首次配置不能启动→独立修改→正确候选得到实际尝试→成功后确认或失败后可继续修复”的完整路径，以及有原责任时仍不能绕过的拒绝路径。不能用“Pending 文件写入成功”作为首配完成标准。

## 6. 统一设置与受控激活

首次向导、运行内设置、离线设置共用字段语义、完整候选构建、验证规则和配置修订；窗口可拥有各自未提交草稿，不拥有另一份生效配置。现有 `StartupConfigurationDraft` 的“原字段保留”策略继续用于不支持编辑的旧拓扑和提供者，不将高级字段摊平成默认值。

一次更改按“读取原修订/hash→编辑草稿→检查差异和影响→保存 Pending→受控停止/启动→资源确认→读回结果”完成。CAS 同时防止另一窗口、维护进程或管理员覆盖原账；异步成功、失败与 finally 都绑定当前编辑代次，旧请求完成不能清新草稿。冲突保留双方信息，用户重新读取比较，不自动采用最后保存者。

字段按真实影响分类：展示偏好即时生效；端点、设备、驱动/组件版本、角色绑定与策略走完整配置候选和受控重启；站/模式/Application/数据根走迁移。页面上显示当前值、待生效值、原因、所需停机和失败结果。选装包安装成功只改变库存，不能立即改绑定；禁用/卸载先查 Effective、Pending、原请求、备份及所有消费者引用，不能删掉仍有责任的包。

受控重启由运行实例完成拒绝新输入、在途状态固化、资源排空和释放，然后由启动层创建下一实例。Stop/Dispose 未成功时保留锁和责任，界面给继续清理/退出诊断入口；不靠强杀进程换取新实例启动。配置激活过程中保持原请求的 payload、目标、合同、包版本和编号，任何新配置只用于被允许的新意图。

## 7. 运行界面、健康、故障与历史

### 7.1 日常任务与状态投影

按作业、记录、设备/服务、设置维护、帮助组织入口，操作员主屏保留当前位、完整条码、原结果、当前阻断和下一步动作。低频版本、内部 ID、合同摘要放详情层；错误详情仍能定位具体请求。主屏、历史、辅助窗口和布局共享 Application 快照，打开只读历史/帮助不重建连接、不发出隐藏暂停命令。

当前可用性、最后业务结果和物理完成分别显示。例如 RCS 获得格口可称“已取得格口”，没有权威实体完成事件时不得称“已完成分拣”；历史已接受结果不因设备离线被改写。输入始终保留字符串身份和前导零；在途重复点击复用原命令身份，忙态新扫描明确拒收并要求重扫，不静默缓存成未知下一件。异步失败保留原输入，焦点恢复到符合当前状态的控件，不抢占用户正在编辑的文本。

权限与登录按产品能力呈现：未启用操作员登录时正常作业入口可用，启用后展示登录/换班/过期状态；维护仍由相应后端规则把关。主按钮固定位置，键盘、扫码与触控流程统一，状态不能只靠颜色；尺寸和 DPI 以真实 WPF/Windows 任务验收为准，不以截图或控件最小高度代替。

主要控件及错误/状态投影同步提供可读名称、标签、当前值、忙态和可用性语义；复用现有 WPF 可访问性机制，新增自绘区域也须可识别。读屏验证并入代表性 Windows 作业旅程，不新增独立测试平台。

### 7.2 可解释健康与可执行故障

健康详情至少分开包已安装、依赖存在、配置已绑定、资源已启动、连接/探测新鲜、业务允许；每个结果关联实际实例、检查时间、epoch 和有效期。缺失、未知、过期和故障都能明确显示，不保留失效绿色。端口恢复不得自动清除原请求、接收责任、存储或人工暂停造成的其他阻断。

故障投影由 Application 的原因和权限产生动作候选，界面不按字符串自行开放“恢复”。对操作员给出影响范围、当前实体、下一步；技术详情含关联身份与证据。设备故障按投递位或共享依赖作用域处理，left 失败不无依据阻塞 right；共享 RCS、存储、全局暂停等按实际依赖阻断。

|故障情形|允许的闭环|禁止的捷径|
|---|---|---|
|设备断连/健康过期|检查设备及绑定，授权重连，刷新新代次健康，再由守卫判断是否可继续|重连后无条件 Resume 或把旧回调接入新连接|
|配置/组件错误|定位原配置与精确包，保存候选、受控激活、读回结果|扫描任意 DLL、自动选参考组件或隐藏缺项|
|外部拒绝|展示原拒绝事实及组件支持的处置，按业务规则处理原件|循环重发相同拒绝意图|
|Unknown/回执资料缺失|保留原请求、原件及责任，按真实合同支持的查询/核对或批准 SOP 处理|通用“重试发送”“强制成功”或换地址重投|
|磁盘不足/存储失败|停止受影响准入，保留原库，按容量/备份/恢复路径处置|删除未决历史、建空库或把收到但未落账结果算作可靠成功|
|停止不完整|继续观察及清理原资源，记录尚持有的责任|解除锁后启动第二实例、假报已停止|

### 7.3 历史查询、导出和指标

当前 Parcel 历史已有按持久序号游标分页、原 Operation 详情和同库不可变归档；优先扩展业务查询契约，不能直接在当前页面内存集合上筛选全部历史。过滤包括时间区间/时区、条码、投递位、结果、请求及异常类别，支持稳定排序和范围内分页；常驻与已归档记录走同一事实源。

导出固定查询条件、字段版本、时间语义和快照范围，使用有界批次/流式写入，限制权限与目标空间，提供进度、取消和错误回执。取消或失败只保留可识别的临时产物，完成后再发布最终文件；不长时间占用作业协调锁。CSV 等面向表格的导出保护公式解析风险并保持条码原值可还原，完整细节按权限提供；导出不能携带凭据或默认整库泄露。

指标名称、分子/分母、统计时间和数据来源随报告交付：识别次数、实体作业数、请求尝试数、格口取得数、拒绝数、待核对数分别统计。同码不同实体不能合并，重试/重复回执不能增加接受量。没有真实完成证据时不输出“分拣完成率”。不先建设脱离现有事实口径的大屏或云分析平台。

## 8. 升级、修复与卸载

升级的检查对象是“程序+Application+契约+精确包集合+配置修订+数据库格式+原责任”，版本号只用于识别。复用现有发行清单、内嵌兼容声明、扩展引用及离线检查；固定快照构建，相关源码、指南、种子和组合声明来自同一提交，禁止工作树混包或给旧 ZIP 改标签。

升级先识别原部署和存储格式，评估未决请求/接收原件/编号/消费者责任，完成匹配原发布要求的处置和完整备份，再进行程序与依赖暂存和受控切换。需要迁移时明确预检、备份、迁移开始/完成记录、失败保持点和可读版本；普通启动不能静默将无法由新版本处理的旧责任迁入未来格式。保持原迁移 SQL/checksum 的历史身份，新格式只追加合法迁移。

如果数据库已执行不可逆迁移，不能承诺“一键换回旧 EXE”。区分程序切回、配置候选失败保旧、数据恢复三个动作。恢复旧备份可能落后于外部事实，必须新根隔离、核对并处理编号范围；程序回退只在当前数据库、配置、包和责任均证明兼容时提供。升级失败后应能从受保护登记、操作回执和完整备份解释当前到底可运行哪个版本。

repair 只修复已选择发布的程序/允许依赖和受损种子输入；沿现有明确 `RepairSeed` 行为保留原种子，既有配置账不被重置。不同版本的 helper 与清单不混用。程序修复不能替代坏库恢复、重新分配 SID 或抹掉旧业务责任。

系统卸载入口默认保留业务数据、配置账、完整备份及审计，先预检当前运行实例和扩展消费者，说明卸载后数据位置与重新安装方式。仅移除确属本安装且不再被引用的程序、快捷方式和系统登记；共享厂商驱动、受信扩展、机器政策与永久租约不得随手递归删除。选择保留旧版本供原请求处理时列清其责任，清理完成后才允许移除。数据销毁为独立维护任务，需要明确范围和既有授权，不与普通卸载默认绑定。

批量安装与人工向导调用同一计划校验/执行内核，支持有版本的应答输入、预检、明确退出状态、重启提示和结构化回执；不得绕过 UAC、独立信任、身份门禁或生产资格。无需实现新的常驻安装服务。

## 9. 备份、迁移与容量

现有 `ParcelRecovery` 已实现完整备份集和新目录隔离恢复，离线界面已有预检/恢复。商业化应完善入口与策略，复用原引擎，不另建“复制 db”备份方法。列表展示备份来源 Application/站/模式、日期、业务与数据库版本、完整性、容量、原件及配置集合和可用恢复范围。

完整备份使用现有一致性快照和 `.recovery/COMPLETED.json`，保留所需原始回执/配置/包引用。自动备份任务也由已有生命周期和维护机制监督，失败需可见，不阻塞 UI 线程或悄悄占满数据卷；触发点、保留策略和目标卷预算写入配置，依据工作站容量制定而非随意默认日数。计划触发仍须满足原备份机制的权限、一致性窗口和责任条件；未满足时记录待执行或失败，不自动暂停生产、不绕过维护认证，也不因此声称支持任意时刻的无干扰在线备份。

恢复保持“只读预检→固定备份身份与目标→授权执行→完整集合核验→隔离标记→重新读取→核对外部事实”。目标必须新建且有容量，原库和原备份保留；部分恢复有明确未完成标记，重启不自动开工。修复或检测期间打开原 SQLite 文件可能产生 sidecar，应继承当前启动维护使用受保护 DB+WAL 副本的做法，并对每个复用的离线入口验证其原文件不变承诺，不因名为“只读”就跳过。

新机器迁移要核对 SID/受信根、实际 SDK、凭据作用域、精确包和资格，不把旧机批准自动转给新机。模板复制只复制配置意图；历史恢复承接原工位责任，两者在入口、记录和结果上区分。迁移必须防止原根与新根同时控制同一设备。

RCS 恢复或克隆需要沿原永久编号归属和范围退役机制处理：退役来源范围包含备份之后可能已经消耗的尾段，新业务取得新的不重叠外部分配范围并沿 CAS/受控激活生效；旧请求仍使用原编号和原报文。不能只读取备份里的最大 ID 后加一来保证安全。

容量界面区分未决工作集、常驻历史、同库归档、DB/WAL、原件、日志、备份及导出。现有同库归档缩减运行内存，不等于释放磁盘；必须据真实可用空间告警并保留关键写入余量。保留策略不得删除仍被未决请求、回执保管、原配置、编号或备份消费者引用的事实。外置归档/磁盘清理若成为本包选择方案，先定义可验证保管、检索和恢复闭环，再开放清理；不以自动删历史掩盖容量问题。

## 10. 诊断、帮助、品牌与复制交付

诊断入口同时覆盖运行内和业务尚未启动的场景。复用现有支持摘要与离线检查，在用户选定时间/对象/内容范围后生成有界诊断包：发行/包/配置摘要、近期结构化日志、健康与失败阶段、相关请求关联、必要安装/维护回执；显式列出包含内容和省略项。默认不含凭据、生产数据库、完整业务报文或客户原件，不自动上传；附件失败不吞错，离线可复制问题编号和保存说明。

帮助随固定版本交付，按安装、首次配置、日常作业、常见故障、备份恢复和升级组织，可离线访问；从故障代码定位本版说明。路径/内部错误/评审编号只放展开详情，不进入正常产品流程。关于页、可执行文件属性、窗口图标、安装器、快捷方式、系统卸载项、诊断包和用户手册使用一致的产品名称、Application、版本及支持标识；生产状态不能由品牌文案伪装。

批量交付使用版本化模板、包/参数允许集合、逐站差异表及每台机器的安装/首配回执。导出模板剥离作业数据、租约、机器策略、凭据及已用编号范围；导入后对站、设备身份、端点、范围和资格执行本地校验，记录来源与覆盖差异。安装器可复用同一静默计划，首次连接和生产验收仍逐实际组合确认。当前按 Application 的单机登记不能直接当作同机无限多工位部署；如确有需求，应先明确注册键、租约和设备独占模型。

授权许可、OEM、多语言、远程支持和多站监控保持条件性扩展：有明确合同或市场需求再沿现有平台边界实现，不无条件加入强制在线激活、常驻云代理或新账号平台。可在当前文案资源、产品元数据和能力开关中保留合理扩展位置，不能为“以后可能需要”拆散已有主流程。

## 11. 实施依赖与交付闭环

先完成文档差额和当前基线，再处理安装信任/路径与独立首配，再统一设置、激活及角色语义。运行 UX、健康与历史可在契约确定后并行推进；升级/卸载依赖安装身份及数据责任，备份/迁移依赖同一配置与恢复规则；诊断、帮助和品牌随每条实际用户路径同步收敛。逐段交付完整可执行路径，不以空页面、服务桩或说明中的 TODO 抵交付。

必要验证按[验收计划](../runtime/validation/commercial-productization-01.md)执行：直接覆盖变更带来的权限、持久化、中断恢复、原请求防重和配置循环风险，复用受影响回归；涉及 WPF/装配/发布时做对应构建和固定媒介冒烟。文案/文档变化不触发无关全量测试；出现具体回归或要求门禁时再扩大范围。不能删断言、忽略必要失败或用静态截图代替原生操作。

交付至少包括实际代码、同版用户指南、配置/部署迁移说明、已知限制、准确 manifest、发行身份和必要验证证据。以实际固定候选验证安装→首配→主流程→故障处理→设置重启→历史/诊断→备份恢复→升级/卸载中本次影响的闭环。缺少 Windows、SDK、协议或现场条件时继续完成不受影响部分，明确 `NOT_RUN`/`BLOCKED`、所需输入和可复现步骤；不能将实现完成、模拟通过、发布字节核验和生产可用混为一个状态。
