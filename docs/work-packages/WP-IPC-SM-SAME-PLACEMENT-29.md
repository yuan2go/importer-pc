# SM-SAME-PLACEMENT-29

2026-11-02，基线 main `b16d3f9`。现场反馈：包裹放上托盘后相机一直读码，一直发送给 RCS，不合理。用户要求从现场交互流程出发修正读码后的请求行为，本包替代此前“各独立有效观察交RCS去重”的条款。

## 现场流程（本包依据）

1. 操作工把包裹条码面朝上放进托盘，托盘位于相机下方。
2. 相机读码后向 RCS 请求格口，格口返回供包台；托盘所在小车带着托盘去指定格口，下一台小车托着空托盘过来。
3. RCS 请求失败时，操作工把包裹取下放到一边，换一个包裹放上去；或把同一个包裹反复放几次，直到取得格口、小车带走。

所以一次“放上托盘”才是一次业务请求，而不是每一帧都是一次请求。

## 规则

- 按工位（左/右）记一次“放置”：第一次被准入的有效条码建立原作业和唯一一次 RCS 请求。
- 同一工位、同一条码在释放窗口（默认 2000 ms，`SportmasterFlow.DefaultSamePlacementReleaseMs`）内持续被读到，视为同一次放置：每帧仍记录为观察（结果 `Duplicate`，原因前缀 `SamePlacement`，指向原作业），不创建作业、不发送 RCS、不计入统计识别/异常。无论原请求结果是取得格口、被拒、超时还是未送达，都一样。
- 条码在本工位读码中消失超过释放窗口后再出现，视为取下后重新放置，按正常准入守卫建立新作业和新请求（满足“失败后重复放几次同一包裹”）。小车带走包裹后同样释放。
- 工位读到不同条码，立即视为新放置。
- 键盘/PDA 人工输入是明确的人工提交，不受该判定拦截；人工准入成功后同样登记本次放置，避免相机随后再读到同一包裹时重复请求。
- 放置判定只用于是否发起新请求；Unknown、原请求冻结、重启后暂停、容量、权限及身份冲突等既有守卫不变。原请求在途时同一包裹的后续帧也记为 `SamePlacement`，不再逐帧记为准入阻断。
- 状态只在内存中，按工位独立；进程重启后首个读码按正常准入处理（重启本身已进入启动暂停）。
- 作业卡：`SamePlacement` 观察指向当前显示的原作业时，不按“重复扫描/未受理”展示，继续显示本次放置的结果（投递格口、正在获取格口、未分配格口及原因）和原作业图片；`DuplicateIdentity` 等其他重复仍按原文案。

## 不变

内置 MVS、进程内 ZXing-C++、内置 RCS、quantity=1、原请求/Unknown、每帧观察留证、无码帧不创建作业、显示随最新观察替换（19/27 包）、跨位独立及调试按轮流程均不变。DirectPlc/WcsToPlc 不启用放置判定（`FlowDefinition.SamePlacementReleaseMs` 默认 0）。

## 待定

释放窗口目前是业务常量。若现场取放节奏或读码间断需要调整，再按参数 V3 共模加入参数项，不在本包新增配置字段。

- 新增 `--same-placement-29`：实际 ZXing、合成 MVS 帧、内置 RCS 回环 HTTP 及 SM 作业卡 ViewModel，10 项：首读请求一次；停留 6 帧不再请求并指向原作业；作业卡保持格口；换码立即请求；被拒后停留不重试且作业卡保持拒绝；取下再放回请求一次；统计按请求计 4 次；右位独立；SDK 帧借还平衡。
