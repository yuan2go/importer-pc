实际计划、索引与复杂度
探针从原HEAD及main直接抽取RetentionClear，使用实际SQL1-9及当前构建的SQLite3.54.0。
DB9有parcel_audit_owner_at(owner,at)、InputObserved OperationId部分表达式索引、
parcel_commands_pending(id)部分索引及commands主键，但没有匹配CommandAdmitted的JSON Owner索引。
原SQL实际计划含SCAN a，按每个候选操作重复扫描审计；此项成本约O(K*A)，
K为候选数，A为审计条数，二者随历史一起增长时会产生二次增长项。
现实现每轮从原审计及命令账派生TEMP待决owner集合，按owner主键查找。
准备阶段仍含一次SCAN a及command主键join，逐作业阶段改为
SEARCH temp.parcel_retention_pending_owners USING PRIMARY KEY (owner=?)。
此项成本由一次准备约O(A+M*log C+M*log P)加K次O(log P)查找组成，
M是命令准入审计数，C是命令账条数，P是不同待决owner数。
这是待决命令归属检查的复杂度结论，不是整个删除流程的RTO证明。
