1. 会不会崩溃、假死、死锁或后台停止无人发现？



不能承诺不会。本轮没有复现产品进程崩溃，也未证实一个必然的托管循环锁死；已经复现按位 worker 异常结束但聚合 HasActiveWork 仍为 true。Snapshot 的 Blocked/失败原因会显示，故不能说所有故障完全隐形；然而它不足以作为每个后台任务存活或业务推进证明。SDK 健康枚举与停止路径可在不可取消 native 调用上等待，UI 同步授权与关闭路径也有无响应风险。应用无响应、进程崩溃和 Windows 整机故障必须分别取证，源码不能保证硬件和操作系统永不死机。



2. 会不会随时间、业务量和操作次数越来越慢？



存在随历史量和常驻工作集增大的成本，尚无当前目标机稳定平台证据。每窗 500ms 的快照会进入全局 gate、计算容量和未决并复制 JSON；部分历史统计与命令过滤扫描 JSON。独立 SQL 微实验显示规模效应，但不是 Windows 性能实测。终态自动归档可控制驻留集合，故不能断言所有集合无限增长；归档仍留在同一 DB，磁盘与启动恢复扫描继续增长。



3. UI、采集、业务和持久化会不会相互阻塞？



会，且应区分路径。常规网络等待期间释放业务 gate，左右位各有队列/worker；UI 主快照通过 Task.Run 进入后台，不是每笔同步网络跑 UI。但是同步日志授权直接卡 Dispatcher，慢快照/SQLite 持 gate 会拖两位；队列溢出的同步落盘在共同 overloadSync 内，维护线程又可持 gate 等该锁，形成慢盘向双位与快照传播的链。



4. 故障后能否隔离、诊断并恢复？



部分能。TCP EOF/非法帧、旧 Epoch、单侧连接失败、停止未排空保留所有权和 RCS 原始响应重建已有有效保护。SDK 不能直接继承 TCP 的隔离结论；RCS 超时保留 Unknown 是正确的责任保护，但当前 real RCS Query=false，缺可执行的权威核对处置。诊断洪峰排空后仍无法 Resume，是另一个已复现恢复缺口。



5. 现有证据支持什么条件、负载和时长？



仅支持冻结源码在 Linux Release 下的定向托管/loopback/替身验证，以及同 tree CI 的有限 Windows Server 2025 原生工程门禁。旧 Windows 11 性能样本属于另一 SourceCommit、300 笔串行合成输入和约 24 秒空闲采样。当前 main 的目标 Windows 11、真实 TCP 双相机、真实 SDK、真实 RCS、正常 24h/72h 均 NOT_RUN。不能给出获证的现场最大吞吐量、最长连续时间或硬件容量。

05 主要风险：按业务影响排序





R01 · P0：worker 失败后，已入内存队列的后续输入没有持久去向



已复现；公共 ParcelRuntime 缺陷。P0 表示交付阻断，不声称现场已丢失业务 Admitted 订单。

触发条件：一位已有外呼/持久化中的第一输入，第二输入被来源回调接收且 Enqueue 返回 true；第一笔在 raw durable 后、T3前发生异常，worker退出。

传播路径：ParcelRuntime 237–245 只有 RAM 入队；247–277 捕获后写 failure 并退出，无逐项残队收口；ParcelCommands 220–267 在 worker 终态异常后仍可释放资源。 [S01] [S02] [S15]

证据与边界：probe-run-02：两次 SourceEmit=true；队列从1保持1；第二笔 audit=0、operation=0，停止释放后重启仍0。第一笔 raw 正确恢复为 SlotResolved/Wcs Accepted且未重发。Dispose报告终结错误并完成释放，非无错关闭；探针直接调用runtime.Dispose，未验证WPF首次关窗。使用12个与冻结Release验证构建SHA256一致的Ipc程序集（含Verification测试程序集），实际ParcelRuntime/Platform/Storage保持原字节；manual/reference端口、故障边界及运行身份预检采用隔离替身，不覆盖生产启动身份门禁。生产T3事务/原件I/O异常可达同一worker退出路径已静态确认；真实磁盘故障NOT_RUN。

业务后果：后续输入已经离开来源接收边界，却既无接纳、拒绝也无未决记录，不能逐笔对账。故障后的整位/共享阻断可见，但“有错误提示”不能补回这笔责任。

修复方向：先更新输入责任契约；在现有队列/原账架构内建立可证明的接收、持久接纳/拒绝或未决转移，以及worker失败/停止/进程异常退出的恢复闭环。若持久化本身失效，需保留来源责任和可核对输入范围；不能吞异常、清队列或把true解释为已完成。



R02 · P1：诊断队列一次满载，当前运行实例无法经管理命令恢复双位准入



已复现；触发频率在现场未测，不把极端合成突发说成日常必然。

触发条件：容量256的诊断队列在写盘来不及时 TryWrite 失败。

传播路径：RuntimeJournal 上报队列满 → ParcelRuntime103 设置共享failure并 accepting=0 → SharedReady/CanAdmit关闭。队列排空不清failure；Resume仍被守卫拒绝。 [S03] [S04] [S05] [S06]

证据与边界：本轮向真实RuntimeJournal注入5000条小元数据（约1.35ms的合成突发）：最终queue=0，accepting=0，左右CanAdmit=false；Pause持久化成功，Resume=Rejected。此测试没有伪造生产业务事件，也没有验证实际日志最大速率。

业务后果：非业务诊断背压升级为整个业务持续停产。恢复要求受控结束并新建运行实例、保留原业务责任；不能绝对说必须重启进程，同进程宿主重建也需单独验证，不能以定时重启代替设计。

修复方向：区分业务审计和可限额诊断；定义有界聚合、丢诊断计数和故障恢复条件。业务原账失败仍必须阻断；诊断失败应有明确状态、监督和经授权可执行恢复，不允许无声吞掉原业务事实。



R03 · P1：原生 SDK 调用开始后不可由现有 token 终止



取消缺口已通过 FakeApi 复现；真实 SDK 永久卡死/原生崩溃为待验证条件风险。

触发条件：枚举、健康探测、Stop/Close/Destroy任一native调用不及时返回，或用户在其开始后取消/关闭。

传播路径：HikrobotReader70–87 Task.Run的token仅影响调度，函数体不检查取消；Stop172–200仅在进入lifecycle时用token，随后等待health并同步native Stop/Close/Destroy；NativeMethods90–108全局枚举锁会串行两台reader。 [S10] [S11] [S12] [S43]

证据与边界：FakeApi受控阻塞：取消已开始Enum后300ms仍未结束，解除阻塞后Start成功/Ready；health Enum堵塞时Stop的100ms token过期、400ms后仍等待。探针结束后释放阻塞并正常清理。没有加载厂商DLL，没有据此声称厂商函数必卡死。

业务后果：停止与受控重启无可证明时限；一台native枚举可使两台健康更新迟滞。若原生异常破坏进程，in-process结构无法仅靠catch保证其余业务。

修复方向：明确native调用所有者、在途回调、句柄释放和未停妥状态；以厂商支持和实测确定边界。若真实API无法给可接受的阻塞/崩溃边界，再评估最小驱动隔离进程，不预设服务化；禁止WaitAsync超时后提前销毁仍使用的句柄。



R04 · P1：SDK 缺失一台相机时，全局启动隔离与 TCP 不一致



静态证实可达；真实两机启动矩阵 NOT_RUN。

触发条件：Hikrobot指定IP/序列号没有枚举到；同进程另一台本可正常运行。

传播路径：HikrobotReader72–73抛IOException；ParcelRuntime165–171只把ObservationConnectionException作为位置依赖隔离；其他异常进入192–200整体启动失败路径。 [S10] [S13]

证据与边界：TCP单侧连接拒绝的定向测试已通过，不能用于此IOException分支。SDK已有清理/异常回抛，但异常分类不符合公共隔离入口。

业务后果：一侧启动缺失可阻止另一侧可用作业位启动。SDK运行期正常Faulted处理和启动期不能混为一谈。

修复方向：在确定native资源已安全收口后，统一可隔离的运输/设备缺失类型；ABI错误、部分句柄未清理等仍应保持整体隔离，不得把所有Exception降级为可继续。仅补缺机、清理失败、单侧启动后恢复的关键测试。



R05 · P1：SDK 帧满载后的拒绝计数及可见诊断不完整



FakeApi已复现；不是当前TCP路径的结论。

触发条件：驱动容量1、消费端暂阻塞，连续三次回调造成满队列，并触发Fault。

传播路径：HikrobotReader119满队列Fault而不计FramesRejected；128在Fault后跳过已排队帧仅更新内部计数；LastFailure私有，ConfirmationSource仅固定SDK标识，宿主健康公开原因不足。 [S11]

证据与边界：合成三帧：FramesReceived=3、deliver=1、FramesRejected=1，存在一帧统计差额；对宿主可见Faulted，但无该错误原因/逐帧责任。不能据此宣称真实设备已经漏单。

业务后果：峰值或下游慢时难以核对来源帧究竟接收、拒绝还是残留；现场只见SDK Fault难以诊断，更不能安全重复触发实体。

修复方向：建立有界的设备Epoch/源序列/拒绝范围与错误分类，确保接收=交付+拒绝+在途；与应用输入责任协议衔接。native回调继续保持短小，不在回调内写DB，也不通过丢帧伪装顺畅。



R06 · P1：溢出 marker 的同步慢盘可横跨双位和业务 gate



静态证实锁内I/O路径；磁盘挂起导致的延迟量 NOT_RUN，未证实循环死锁。

触发条件：一位队列满，同时数据卷慢、Flush或文件移动迟滞。

传播路径：Enqueue持共同overloadSync调用AtomicWrite；后者WriteThrough/Flush(true)/Move。Maintain每100ms持业务gate进入RecoverOverloadAcknowledgement，再等待overloadSync。 [S01] [S07] [S08] [S09]

证据与边界：队列有界与durable overload标记本身是保护；漏洞是外部I/O在跨位共享锁内。没有通过移除marker来取得通过，也未做真实磁盘注入。

业务后果：一侧过载拖住另一侧采集回调，进一步拖住持gate的业务/状态快照；UI可因等待快照显得停滞。

修复方向：分离即时内存屏障与具有单一所有者的有界持久化责任，设计marker失败状态/恢复流程；不得在共享回调锁或gate内等待慢文件系统，不得丢掉已判定的过载责任。



R07 · P1：RCS Unknown 安全阻断已有，恢复合同尚未闭环



静态证实合同缺口；这是业务恢复阻断，不是程序死锁。

触发条件：任务POST已可能生效，但超时、错关联、异常/非法响应或连接中断，结果不能确定。

传播路径：Service将不确定结果保留Unknown；real RCS能力Query=false，QueryAsync不发原请求；Unknown不可按“未提交”弃置，本位后续准入关闭。共享心跳恢复不解决原Unknown。 [S14] [S15] [S16] [S06]

证据与边界：本轮sportmaster-rcs验证确认原requestId/body/target保存、不会自动重发；这是正确保护。未提供真实RCS可查询/签认处置协议与实际恢复演练。

业务后果：若现场期望断网恢复后继续生产，现有流程不能仅凭TCP/心跳变绿恢复未决责任。一笔Unknown可长期阻塞本位；共享RCS健康失败会阻两位。

修复方向：先与RCS及业务责任方确定基于原requestId的权威结果查询、经验证的结果导入或人工对账处置契约，再在现架构实现可审计恢复。不能自动改ID重投、重POST、清库或丢Unknown。



R08 · P1容量门槛：快照/历史/恢复成本随数据量增长

触发条件：常驻接近200、历史/完成命令长期累积，双窗刷新并发记录查询、筛选、统计或导出。

传播路径：Snapshot在gate内反复容量计算、PendingCommands JSON过滤、完整JSON克隆；历史Page/Metrics按JSON字段扫描/汇总；读事务贯穿页面/统计调用，ReadHistoryAsync无取消参数/统一并发上限。启动又逐历史复核数值ID和恢复标志。 [S18] [S19] [S20] [S21] [S22] [S31] [S32] [S33]

修复方向：先定目标历史量/延迟预算，复用现账增加适配索引/可信增量投影，精简运行快照，详情按需；查询执行取消、并发和导出期限应覆盖底层工作。迁移与完整核验不可被无证据跳过。

静态证实；不是MaximumOperations累计耗尽缺陷。

R12 · P1/P2：关闭预算、日志任务与底层 I/O 所有权未完整收敛



静态证实；磁盘/native挂起下的真实关窗行为 NOT_RUN。

触发条件：窗口关闭时有慢日志导出、日志append、SDK停止或其他不可取消I/O。

队列、吞吐与等待时间



默认每位queue64、ResidentHistory200、MaximumOperations10000、TimeoutMs1500。MaximumOperations不是累计历史总件数。稳定持续输入至少要求每位长期到达率lambda小于可持续服务率mu，峰值积压需在业务时限内消退。64个槽位不等于可接受64件任意等待；近似等待q/mu只是容量估算，必须同时测最老年龄、服务时间分布和恢复后积压。现场lambda、峰值长度和决策截止未知，本报告不报“支持X件/秒”。



磁盘、历史与备份



可外推天数 = 可用于增长的字节 /（实测每件增量 × 双位总件/秒 × 86400 + 日固定增量）。可增长空间必须先扣系统最低余量、WAL最坏增长、完整备份/恢复集、故障诊断和迁卷操作空间；默认64MiB仅技术守卫，不能替代预算。归档保留责任原账，不能当空间回收。人工padding的SQL数据库体积不能作为真实每件增量。 [S19] [S28] [S29]

需要在目标Release/组合下以多时间窗拟合数据库、raw、日志、备份的单位件增长，并按承诺留存量预置规模验证查询和冷恢复。若备份要求连续作业期间无人值守完成，应先更改当前“Paused+管理授权”政策/实现；若允许维护窗口，应明确窗口频率、截止告警和错过后的处理。保留未决与历史身份，不能删除来恢复表面正常。



内存、线程与句柄



已看到很多计数边界，未实测长期保留泄漏。Hikrobot默认128帧，每帧最多300×4096字节码；按独立最大ASCII字符串转UTF16估算，仅驱动字符载荷可约300MiB/相机，属于极端理论预算，非常态工作集或总进程上界，不含对象/native/临时分配且可能有共享。应用还会裁剪候选长度/数量；应补按字节的预算和峰值观测，不能只看“队列128”。 [S11] [S43]

预热后按固定输入量和时间窗口观察托管堆、Private Bytes、分配率、GC暂停、线程、handles、GDI/USER及故障恢复后回落。首尾工作集、总分配量或一次强制GC均不能判定/排除泄漏。UI/辅助窗口反复开关、订阅/CTS释放和native回调寿命必须在Windows实际组合验证。
